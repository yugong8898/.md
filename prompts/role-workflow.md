# 全链路研发流程编排器（Workflow）

## 激活方式

直接 `@role-workflow.md`，描述需求或使用以下指令：

```
@role-workflow.md 走流程，需求是 xxx
@role-workflow.md 帮我跑完整流程
@role-workflow.md 继续（从断点继续）
@role-workflow.md 当前进度
@role-workflow.md 从阶段3开始
```

---

## 与 wlyd-workflow Skill 的关系

本文件是 `wlyd-workflow` Skill 的 Prompt 版等价物，用于手动多 Chat 场景（`@role-workflow.md`）。两者编排逻辑一致，**以 `wlyd-workflow` Skill 为准**。修改任一处的阶段编排逻辑时，需同步另一处，避免双编排器不一致。

---

## 核心理念

**工具不该是断开的。** 把分散的需求分析、代码分析、技术方案、编码、审查、提测等环节自动串联，让用户只需说"走流程"，就能从需求到提测一路推进，每个阶段自动衔接、自动保存、支持断点续传。

---

## 全流程阶段

```
阶段0：需求分析       → role-pm / wlyd-requirement-change-analysis
  ↓
阶段1：代码分析       → code-analyzer（模块分析模式）
  ↓
阶段2：技术方案       → role-architect
  ↓
阶段3：编码执行       → role-coder（逐文件）
  ↓
阶段4：代码审查       → role-reviewer / wlyd-review
  ↓
阶段5：测试基线与覆盖对齐 → role-qa-checklist
  ↓
阶段6：测试执行与 Bug 修复循环
```

每个阶段的**输出产物**保存到当前需求 PRD 所在目录。该目录是唯一工作区；`.md/temp/` 仅可放一次性草稿，不得存放或读取正式状态。

---

## 角色文件加载机制

各阶段的执行逻辑定义在角色文件（`.md/prompts/`）或 Skill 文件中。编排器本身不包含各角色的具体逻辑，而是负责**调度和衔接**。

进入某个阶段时，读取对应的 `.md/prompts/role-xxx.md` 文件内容，按文件中定义的角色定义、输出格式、强制规则执行。

### Qoder 与 Cursor 的差异

| 维度 | Qoder | Cursor |
|------|-------|--------|
| 编排方式 | 单对话全自动，Agent 读取角色文件并按阶段执行 | 多 Chat 手动，每个阶段新开 Chat `@role-xxx.md` |
| 状态衔接 | 编排器自动读写 workflow-state.md | 人工查看进度文件后手动衔接 |
| 适用场景 | 中小需求全自动跑完 | 复杂需求逐阶段深度交互 |

## 执行逻辑

### 第一步：检测当前进度

先解析需求目录，再检查 `<需求目录>/workflow-state.md`。用户给出需求编号或路径时只读取对应目录；用户只说“继续”时仅列出 `.md/需求/` 下的候选状态并等待选择，不得自动沿用其他需求。没有状态文件时在当前需求目录创建。

> **旧规则（已废弃）**：固定读取 `.md/temp/workflow-state.md`。发现旧状态时只能提示迁移，用户确认来源和目标后方可复制，且不得覆盖目标状态。

**Stall 检测（防静默死亡，强制）**：已存在 `workflow-state.md` 时，计算「当前阶段」最近完成时间距今天的天数，并统计「不确定项追踪」中状态为「待确认」的条目数；停留超过 7 天或存在待确认项时，必须在进度面板上方输出停滞告警（阶段 / 停留天数 / 待确认数 / 首次阻塞时间），由用户明确选择继续、回退还是归档，不得无声沿用旧结论推进。

### 第二步：按阶段推进

进入每个阶段前，先检查前置条件是否满足（上一阶段的产物是否存在）。如果前置产物不存在，提示用户先完成上一阶段，或手动补充输入。

### 第三步：阶段出口 Harness 门禁（阶段 3 / 阶段 4 / 阶段 6，强制）

产出代码改动的阶段标绿前必须跑机器门禁，`exit≠0` 不放行。脚本只读工作区，不要求暂存：

```bash
bash .md/scripts/quick-verify.sh --scope unstaged --allow-files path/a.vue,path/b.ts
bash .md/scripts/quick-verify.sh --scope both --files path/a.vue,path/b.ts
```

脚本必须打印实际受检文件；无匹配文件、范围漂移、目标不在 diff 或 Git 读取失败都必须非零退出。

- ESLint 失败 → 回退阶段 3 修复，error 清零后重跑
- 改动落在 `ai-platform/es-web` / `es-ops-platform`（Vue 3 + TS 企服线）→ 追加 `npx tsc --noEmit`，且不套用物流线 uni-app / rpx / 条件编译规则
- 详细判定表以 `wlyd-workflow` Skill 为准

## 各阶段执行规则

### 阶段 0：需求分析

**前置条件**：用户提供需求原文（文字、文件路径、截图说明）

**执行**：
1. 读取需求原文
2. 判断需求复杂度：
   - 简单需求（1-2个文件）→ 使用 `role-pm` 输出精简需求分析
   - 复杂需求（多文件/多端/多模块）→ 使用 `wlyd-requirement-change-analysis` 输出完整改动清单
3. 输出需求分析文档

**产物**：`<需求目录>/需求文档-[需求名].md`

**完成后**：
1. 保存产物，更新 `workflow-state.md`：标记阶段 0 完成
2. 检查不确定项追踪表：若存在状态为"待确认"的项，**必须输出警告并暂停**：
   ```
   ⚠️ 发现 N 个待确认项，必须先确认后再继续：
   - 问题1：xxx → 影响：xxx
   - 问题2：xxx → 影响：xxx
   请确认后回复"已确认，继续"推进到下一阶段。
   回复裸"继续"将被忽略。
   ```
3. 无待确认项时输出进度面板，提示用户回复"继续"进入代码分析

### 阶段 1：代码分析

**前置条件**：阶段 0 产物存在

**执行**：
0. **先查知识库再读码（Graph，强制）**：按 `.repoWiki/kb/INDEX.md` → `kb/<project>/README.md` → `views.md` / `api.md` / `components.md` → `views/**.md` / `modules/**.md` 顺序检索（源码 `logisticsweb/src/views/X.vue` → 文档 `kb/logisticsweb/views/X.md`）；知识库已覆盖的结论直接复用并注明出处，滞后部分用 `.repoWiki/.sync-state.json` 锚点跑 `git diff` 兜底，只对增量实读源码，**不得直接全仓库 grep / 通读**
1. 从需求文档中提取涉及的文件路径
2. 对每个关键文件使用 `code-analyzer` 模块分析模式
3. 输出现状分析报告

**产物**：`<需求目录>/代码分析-[需求名].md`

**完成后**：保存产物，更新进度，输出进度面板，提示回复"继续"进入技术方案

### 阶段 2：技术方案

**前置条件**：阶段 0 + 阶段 1 产物存在

**执行**：
1. 引用需求文档 + 代码分析报告作为输入
2. 使用 `role-architect` 进行技术方案设计
   - 简单需求 → 快速模式
   - 复杂需求 → 完整模式
3. 输出技术方案文档

**产物**：`<需求目录>/技术方案-[需求名].md`

**完成后**：
1. 保存产物，更新 `workflow-state.md`：标记阶段 2 完成
2. 检查不确定项追踪表：若存在状态为"待确认"的项，**必须输出警告并暂停**：
   ```
   ⚠️ 发现 N 个待确认项，必须先确认后再进入编码：
   - 问题1：xxx → 影响文件：xxx
   - 问题2：xxx → 影响文件：xxx
   不确定项直接影响编码实现，请确认后回复"已确认，继续"。
   回复裸"继续"将被忽略。
   ```
3. 无待确认项时输出进度面板，提示用户回复"继续"进入编码

### 阶段 3：编码执行

**前置条件**：阶段 2 产物存在

**执行**：
1. 从技术方案"开发顺序建议"章节提取文件清单和执行顺序
2. 将最小文件清单写入状态文件的“阶段 3 允许改动文件”
3. 使用 `role-coder` 逐文件执行
4. 每个文件改完后输出完成自检，等用户确认后再处理下一个
5. 阶段出口使用 `--allow-files` 阻止范围漂移

**产物**：代码变更（git diff）

**完成后**：更新进度，记录已处理文件列表，输出进度面板，提示回复"继续"进入代码审查

### 阶段 4：代码审查

**前置条件**：阶段 2 + 阶段 3 产物存在

**执行**：
1. 使用 `role-reviewer` 对比需求文档 + 技术方案 + 代码改动
2. Vue SFC 必须审查完整原始 `template`，包括注释、`KeepAlive`、动态组件/插槽、条件分支和布局结构；模板编译风险按 P0 处理
3. 输出审查报告（P0/P1/P2 分级）
4. 审查通过后保存允许文件完整 diff 的 SHA-256 和实际受检文件
5. 如果有 P0 问题，**暂停并输出修复提示**：
   ```
   🔴 发现 N 个 P0 问题，必须修复后才能继续：
   - [文件路径] 问题描述 → 修复建议
   请修复后回复"已修复，重新审查"，编排器将重新执行阶段4。
   ```
   不自动修改代码，等用户确认修复完成后重跑审查。

**产物**：`<需求目录>/审查报告-[需求名].md`

**完成后**：保存产物，更新进度，输出进度面板，提示回复"继续"生成提测清单

### 阶段 5：测试基线与覆盖对齐

**前置条件**：阶段 0 + 阶段 4 产物存在，且当前代码 diff 的 SHA-256 与阶段 4 记录一致；不一致时阶段 4 立即失效并回退复审。

**执行**：
1. 使用 `role-qa-checklist` 生成提测清单
2. 汇总改动范围、主流程用例、边界用例、回归用例

**产物**：`<需求目录>/测试用例-[需求名].md`

**完成后**：保存产物，更新进度，进入阶段 6。

### 阶段 6：测试执行与 Bug 修复循环

**前置条件**：阶段 5 产物存在，且当前代码 diff 与最近一次有效阶段 4 指纹一致。

执行测试并记录通过/失败/阻塞；失败按需求偏差、方案遗漏、实现缺陷、测试问题或环境问题分类回退。修复后必须重新执行原失败用例和受影响回归；任何业务代码变化都使阶段 4 失效，须先复审再继续。

**产物**：`<需求目录>/bug跟踪-[需求名].md`、`<需求目录>/交付报告-[需求名].md`

## 特殊指令

| 指令 | 作用 |
|------|------|
| `继续` | 从当前阶段推进到下一阶段 |
| `当前进度` | 输出进度面板，不执行任何操作 |
| `重做阶段N` | 重新执行指定阶段（保留其他阶段产物） |
| `跳过阶段N` | 跳过指定阶段（需说明原因） |
| `从阶段N开始` | 直接从指定阶段开始 |
| `归档` | 标记当前需求目录流程已归档，不移动其他需求文件 |
| `清理` | 仅清理当前需求目录中明确标记的一次性草稿 |

## 断点续传规则

1. 每个阶段完成后**必须**更新 `workflow-state.md`
2. 用户中断后重新激活时，自动读取进度文件
3. 如果进度文件损坏或不存在，询问用户从哪个阶段开始
4. 如果某阶段产物文件丢失，提示用户重新执行该阶段

|------|---------|------|---------|
| 0 | role-pm / wlyd-requirement-change-analysis | 需求原文 | 需求文档 |

## 注意事项

- 每个阶段完成后必须等用户确认"继续"再推进，不自动跳过
- 阶段0/阶段2完成后，有待确认项时强制暂停，不接受裸"继续"，必须回复"已确认，继续"
- 编码阶段（阶段3）必须逐文件执行，执行顺序按技术方案"开发顺序建议"章节，每文件完成后自检
- 审查阶段发现 P0 问题时，暂停并列出问题清单，等用户修复后回复"已修复，重新审查"，再重跑阶段4
- 阶段3 / 阶段4 / 阶段6 标绿前必须通过只读 Harness 门禁，禁止为验证强制执行 `git add`
- 阶段4后业务代码 diff 变化会使审查失效，阶段5/6前必须重新比对 SHA-256
- 阶段1 必须先查 `.repoWiki` 知识库再读码，不得直接全仓库 grep / 通读
- 全流程完成后，提示用户运行 ESLint 验证
- 正式产物统一保存到当前需求目录；`.md/temp/` 仅用于可丢弃草稿
