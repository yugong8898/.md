## 一、使用说明与答题总策略

**定位**：资深前端 / 前端 Owner。答题永远往"业务理解 → 方案设计 → 边界处理 → 结果验证"四层走，不背 API。

**答题公式**：一句话结论 → 背景约束 → 我的方案与取舍 → 边界/异常怎么处理 → 结果与沉淀。被追问不会的，承认边界后立刻转移到相邻的实践经验（参考 `docs/框架原理面试话术.md` 第五章策略）。

**配套文档**：
- 通用八股（React Fiber/Hooks/Vue 响应式/Redux）：`docs/框架原理面试话术.md`
- JS 核心与手写题、复习计划：`docs/前端面试准备指南.md`
- 本文档：简历上每个卖点的深挖题 + 第一人称话术 + 追问预案。

**练习方法**：每个项目先把"30 秒版本"讲熟（背景一句 + 我做了什么两句 + 结果一句），面试官感兴趣再展开细节。细节全部来自真实交付，可放心展开。

## 三、项目深挖题库与话术

### 3.1 TMS 结算迁移与资金治理

**Q1：讲讲这个迁移，难在哪？**

> 难点不是写代码，是"迁移期新旧系统并行，资金数据不能错，下游不能感知"。42 个接口从旧 TMS 迁到撮合域，返回结构、字段命名、错误码都不完全一致，但 5 个核心列表页和 20 多个下游组件是按旧契约写的。我的方案是三层：接口级灰度开关控制每个接口走新走旧；统一响应归一化层把新接口返回适配成旧契约形状；三层静默兜底保证新接口异常时回落旧链路。这样下游组件零改动，任何一个接口出问题可以单独回切，不用整体回滚。

**追问：灰度开关怎么设计的？**
> 开关粒度到接口而不是页面，配置化下发。切换前新旧接口双跑比对返回，确认一致再放量；出问题关单个开关即回旧链路，用户无感。

**追问：怎么验证迁移正确性？**
> 三道：类型基线零新增门禁保证契约类型不破坏；断言脚本对归一化层做输入输出校验；分端走查留证据。资金相关额外做 BigNumber 等式校验，允许 ±0.01 误差。

**Q2：为什么金额要用 BigNumber？0.1+0.2 为什么不等于 0.3？**

> JS 数字是 IEEE 754 双精度浮点，0.1 和 0.2 转二进制都是无限循环小数，存储时截断产生误差，相加后误差暴露成 0.30000000000000004。金额场景这个误差会导致等式校验误判、对账不平。我们的做法是计算全程走 BigNumber，展示和输入用字符串，避免 number 和 string 混用；校验允许 ±0.01 的容差。另一个实战坑：清零时如果赋 number 0，和输入框的字符串 '0.00' 类型不一致会引发联动 bug，所以清零统一用字符串。

**追问：还有别的方案吗？**
> 整数分存储（金额×100 用整数算）也能解决，但前后端契约要一起改；BigNumber 是前端侧最小改动方案。精度要求极高的金融核心一般后端用 BigDecimal，前端只做展示级计算。

**Q3：小计变化导致到付为负，和回单付变化导致到付为负，处理一样吗？**

> 不一样，这是我们踩过的坑。公式相同但触发来源不同，产品定义的交互不同：有的来源要清空冲突字段，有的要回退输入并标红提示。所以不能抽一个"负值统一处理"函数了事，必须按触发来源分支处理。这件事后来固化成我们的规则：相似场景必须区分触发来源，逐一确认交互。

### 3.2 电子签章多端落地

**Q1：四端落地怎么保证行为一致？**

> 先做全量出口排查：PC/H5/小程序/APP 每端的接口封装和 handler 是独立的，不能只 grep 一个共享函数名就下"另一端没有"的结论。我们逐端枚举 api 目录的封装函数、views 里的 handler，追全部消费点，确认每个签署入口都接了守卫。架构上把身份分流和签署状态判断收敛到共享逻辑，各端只做渲染差异；交互形态按"承载页面"维度判定，而不是按触发来源——这两个维度语义不同，混用会出 bug。

**Q2：请求竞态怎么防的？**

> 场景是用户快速切换身份/单据，先发的请求后返回，把页面状态覆盖成旧数据。方案是请求序列号：每次发起递增序号，响应回来比对序号，过期的直接丢弃。配合入口守卫——状态不满足签署条件时入口直接拦截，不让无效请求发出去。

**追问：为什么不用 AbortController？**
> AbortController 能取消请求但取消不了"已发出正在途"的响应处理时机问题，且小程序端兼容性不一；序列号方案不依赖平台能力，四端通用。两者可以叠加，序列号是兜底。

**Q3：多身份分流具体怎么设计？**

> 雇主、司机等身份对应不同的签署流程和状态机。进入页面先解析身份与单据状态，路由到对应分支；每个分支的可签署条件、按钮文案、跳转目标独立配置。关键教训是 UI 判定维度必须和产品书面确认——我们曾因把"承载页面"误判成"触发来源"返工两轮，后来固化成规则：按钮文案/入口显隐类差异，维度未确认不落码。

### 3.3 啫喱微前端运营后台

**Q1：为什么用微前端？qiankun 原理讲讲？**

> 运营后台按业务域拆给多个团队并行迭代，单体应用会互相阻塞发布，所以主应用 + 7 个域子应用。qiankun 基于 import-html-entry：fetch 子应用 HTML，解析出脚本和样式，在沙箱里执行。JS 沙箱用 Proxy 拦截 window 的读写，子应用改的全局变量记在自己的 fakeWindow 上，卸载时还原，互不污染；样式隔离有严格模式（Shadow DOM）和实验模式（给选择器加作用域前缀）两档。子应用导出 bootstrap/mount/unmount 生命周期，主应用按路由激活。

**追问：子应用间怎么通信？**
> 主应用 initGlobalState 挂全局状态，子应用 onGlobalStateChange 订阅；轻量场景用 props 下发宿主能力（我们主应用通过 props 暴露导航、token、埋点、上传校验）。跨子应用跳转用 sessionStorage 记来源参数 + 自定义事件，存储异常 try/catch 降级。

**追问：子应用公共依赖怎么处理？**
> 我们把 vue/element-plus 这类运行时单独打包成 runtime-vendor 供子应用复用，避免每个子应用各带一份。React 体系同理可用 externals + 主应用注入。

**Q2：微前端踩过什么坑？**

> 三类：一是子应用 publicPath 要运行时动态设置，否则静态资源 404；二是路由基座和子应用路由映射要统一维护，刷新/直达子应用路由时状态会丢，我们做了路由状态管理器；三是 keep-alive 场景子应用卸载不彻底会残留全局监听，卸载钩子里必须清干净。

### 3.4 App Hybrid 与站外增长 H5

**Q1：Hybrid 容器怎么搭的？价值是什么？**

> 充值、商城、会员这类业务变更频繁，走客户端发版太慢，所以用 WebView 内嵌 H5。我从 0 搭了 Umi Max + TS 的容器工程：统一登录态对接、Sentry 监控、多语言出入口、nginx 部署。核心价值是业务页脱离客户端发版节奏独立上线，出问题回滚 H5 即可，不用发版。

**追问：H5 和 Native 怎么通信？**
> JSBridge 常见三种：URL Scheme 拦截（WebView 拦截特定协议）、prompt 拦截（Android）、messageHandler（iOS WKWebView）。我们站外唤端用 URL Scheme + 下载兜底：定时内未唤起说明没装 App，跳下载页。

**追问：Hybrid 性能怎么优化？**
> 常规手段：离线包/预加载减少白屏、骨架屏、图片懒加载、首屏关键请求前置。监控上 Sentry 抓 JS 错误，配合性能打点看白屏时长。

**Q2：站外增长链路怎么做的？**

> 分享详情页是传播入口，页面里做 Scheme 唤端 + APK 下载页兜底，路由监听处理前后台切换后的状态恢复，主题色跟随产品配置。整条"分享→唤端→下载"链路闭环，文案多语言。

### 3.5 Web3 数字藏品平台

**Q1：gas 费预估为什么从 ×10 改成 ×1.5？**

> 早期预估 gas 直接乘 10 做缓冲，用户实际多付很多，体验差还容易被投诉。分析后改成 ×1.5：gas 预估本身是模拟执行，偏差主要来自执行间隔内的链上状态变化，1.5 倍足够覆盖正常波动；EIP-1559 下用户设的是 maxFeePerGas 上限，实际按 baseFee + priorityFee 扣，多设的部分会退还，所以缓冲不需要那么激进。

**追问：EIP-1559 讲讲？**
> 交易费 = baseFee（网络动态调整，销毁）+ priorityFee（给验证者小费）。用户提交 maxFeePerGas 和 maxPriorityFeePerGas 两个上限，实际扣费不超过上限，差额退还。相比 legacy 的单一 gasPrice，费用更可预测。

**追问：Arbitrum L2 有什么不一样？**
> L2 的 gas 结构多了 L1 数据费（calldata 上主链的成本），gas 单价量级和主链不同，预估参数要分链配置，不能一套参数打所有链。我们合约地址和 chainId 配置化，切链不动代码。

**Q2：钱包安全怎么考虑？**

> 助记词是资产根密钥，只在本地处理不上送；转账前展示明细二次确认；购买前校验钱包连接状态防误操作；交易给 Etherscan 链接可追溯。后台侧做滑点预估和价格保护，防止发售时价格异常造成资损。

### 3.6 Bondee 国际官网

**Q1：8 语言怎么管理的？**

> 文案走 locales 文件（英/日/韩/繁中/越/印尼/泰/马来），内容型文案（新闻、公告）走按地区的 config 文件，新增地区只加配置不动业务代码。边界坑：日语有独特排版习惯，不能和中文共用断行逻辑，单独处理。

**Q2：SEO 做了什么？**

> head 的 title/description 按页面和语言配置、图片 alt 国际化、html lang 属性正确声明；静态资源从自建静态域迁到 GSLB 全球 CDN 多域名分发，各地区访问速度均衡。Next.js 侧用 SSG/静态预渲染保证爬虫拿到完整 HTML。

**追问：SSR 和 SSG 怎么选？**
> 内容站更新频率低用 SSG，构建时生成 HTML 上 CDN，性能最好；需要实时数据的用 SSR（getServerSideProps）；折中用 ISR 定时再生成。官网内容站主体 SSG，活动页按需 SSR。

### 3.7 茅台全端（RN/小程序/Node）

**Q1：RN 长列表性能怎么优化？**

> 列表用虚拟化（只渲染可视区）、图片层升级 CachedImage 做缓存避免重复下载解码、列表项 memo 化减少重渲染。双端差异单独治理：Android 字体缩放要关 allowFontScaling，键盘搜索键行为两端不一致要分别处理。

**追问：RN 老架构原理？**
> 三个线程：JS 线程跑业务、Native 线程跑原生、Shadow 线程算布局，中间靠 Bridge 传 JSON 序列化消息，通信开销大——这也是新架构改 JSI 同步调用的原因。我们项目是 0.59 老架构，优化重点就是减少 Bridge 消息量。

**Q2：小程序双线程模型讲讲？Taro 和 uni-app 什么区别？**

> 小程序逻辑层（JsCore）和渲染层（WebView）分离，setData 是两层间序列化通信，频繁/大量 setData 是性能头号杀手，所以要合并更新、只传 diff。分包控制主包 2M。Taro 是编译时把 React/Vue 语法转成小程序模板 + 运行时适配层；uni-app 是 Vue 语法 + 条件编译，一套代码出 H5/小程序/APP。我们会员小程序用 Taro，货主端用 uni-app，两套都交付过。

**Q3：Egg.js 日报服务怎么设计的？**

> Egg 基于 Koa，中间件洋葱模型。日报用 schedule 定时任务：聚合门店经营数据 → 服务端渲染海报（模板 + 静态资源）→ 邮件推送。定时任务与 Web 工程分离部署，生产数据库配置独立管理，避免任务拖垮在线服务。

## 四、AI 工程化专项题

**Q1：你搭的 AI 研发体系具体是什么？**

> 四块：一是七阶段工作流（需求分析→代码分析→技术方案→编码→审查→提测→复盘），支持断点续跑，每阶段有产物和门禁；二是多 IDE 规则同步，一套规则源镜像到 Cursor/Qoder/CodeBuddy/Trae，脚本校验一致性；三是分层知识库，git 驱动增量维护，编码前先查库再读码；四是 MCP 工具链，接 Apifox 契约、Figma 设计稿、云效缺陷、飞书文档。配套坑点库和复盘机制，同类错误不二犯。

**Q2：怎么防止 AI 写错代码？**

> 三道闸：事前——接口契约四件套（字段名/类型/嵌套层级/旧参数行为）书面确认才落码，不确定项 TODO 占位不许脑补；事中——影响分析双轨制，grep 现有消费点 + 按业务语义推演潜在页面，负结论必须附搜索式；事后——类型基线零新增门禁 + 断言脚本 + 分端走查留证，静态检查和人工验证分开记录，不伪造全通过。实际踩过的坑（比如只 grep 一个函数名误判另一端无链路）都固化成了规则。

**Q3：效果怎么衡量？**

> 不拿提交次数说事，看交付结果：需求按期上线率、迁移类需求下游零改动、线上资金零事故、返工轮次下降。体系的价值是把"个人不犯错"变成"团队不犯同类错"——12 篇 SOP 和坑点库是团队共享资产。

**Q4：这套东西到新公司怎么落地？**

> 先落最小闭环：规则文件 + 契约确认流程 + 改动前横向搜索，这三样不依赖工具栈，一周内就能在团队跑起来；知识库和 MCP 集成按团队现有工具渐进接入。我不主张一上来全套照搬，先解决最痛的返工问题。

## 六、高风险红线清单

1. **禁用包装数字**：旧面试文档里"首屏 3.5s→1.2s、FPS 30→55"等无实测佐证，一律不说。被问性能优化只讲手段和定性结果，除非有真实测量。
2. **REQ-133 二级频道不说"已上线"**：已交接，本人交付至主体开发部分。被问就如实说"完成主体开发后交接，后续由同事跟进"。
3. **不拿提交次数当卖点**：衡量口径是交付结果（上线/零事故/覆盖范围），提交数据只是内部 backing。
4. **空窗与短任期如实说**：用第二章模板，不编造理由；离职原因按真实情况填。
5. **公司名/学历占位符**：面试前必须把简历 5 处【待填】补齐，简历与口述一致。
6. **不会的题承认边界**：说"这块我实践里没深入到，我的理解是……，实际项目里我是这样处理的……"，不硬编。
