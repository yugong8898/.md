## 一、方案结论与边界

### 1.1 推荐方案

保留原始 `orderType`，新增页面 checkbox 与服务端权限状态；仅将“实际创建类型”用于创建请求、创建后分支和本页业务类型埋点。三个下单前接口继续读原始入口类型。

同时补齐与本需求直接相关的异步和生命周期边界：提交全程锁定、保证金关闭时取消本次提交、同路径不同 query 重新初始化、已创建订单不重复创建。

计划修改三个既有文件：确认页、预览响应类型、布局中仅针对确认页的路由 key。第三处是现状核查后提出的技术改动，尚待本轮方案验收；不代表用户已经授权修改公共布局。

### 1.2 方案比较

| 方案 | 取舍 | 结论 |
|---|---|---|
| 原类型不动，新增有效创建类型与局部快照 | 多一个页面派生值，但三接口与原需求链路边界清晰 | 采用 |
| 直接把现有 `orderType` 改成可写／随 checkbox 变化 | 会改变试算、价格 watch、保证金及原需求链路 | 不采用，违反 R-009 |
| 把模式放进 URL／Pinia／本地存储 | 扩大状态范围，容易记忆旧选择、改写入口来源 | 不采用，违反不记忆与最小范围要求 |

页面重进采用“仅确认页使用完整路由 key”：比在 buy.vue 手动维护商品、数量、优惠券、弹窗、订单 ID 等多组 reset 更直接；其他页面仍使用原 path helper。只在 mounted 重置 checkbox 则无法覆盖同路径 query 更新，不采用。

### 1.3 非目标

不新增接口、订单字段、订单状态、标签管理、支付方式或合同流程；不修改三个前置接口参数；不重构整个 buy.vue；不治理跨页面埋点；不增加 APP／服务商／运营及列表／详情新展示；不更新知识库、规则、依赖或锁文件。

## 三、状态与接口设计

### 3.1 页面状态

| 名称 | 类型／初值 | 职责 |
|---|---|---|
| `orderType` | 既有 computed number | 原始入口类型；不改定义，不写回 URL |
| `signBeforePay` | ref boolean，false | checkbox 选择；不进 store／storage／query |
| `canChangeOrderType` | ref boolean，false | 最新有效预览的严格布尔权限 |
| `confirmPreviewReady` | ref boolean，false | 预览业务成功、商品存在且状态有效后才为 true；不是价格接口的新业务状态 |
| `showOrderTypeOption` | computed boolean | 原始类型为1、没有已有需求 ID、且服务端权限为 true |
| `createOrderType` | computed number | 允许展示且勾选时为2；否则保留原始 orderType，不统一回退为1 |
| `submitting` | 复用既有 ref | 从首次异步前持续到本次提交退出；保证金等待期间不释放 |
| `submittedOrderType` | handler 内局部 const number | 本次有效选择快照；创建参数、成功分流、本页类型埋点共同使用 |
| `currentOrderId` | 复用既有 ref | 有有效创建结果后保留；不因签约／支付失败清空并重新创建 |
| `pageDisposed` | 页面内 boolean，false | 卸载后为 true；异步恢复时停止本页后续副作用，不存储 |

已有需求 ID 的异常混合链接即使携带类型1，也不开放新的切换入口；保留其原类型和原校验，不自行改成2。报价 ID 或商机 ID本身不等于需求 ID，不据此屏蔽所有 IM 直采。

有效类型关系：

```text
原始类型1 + 无需求ID + 权限true + 已勾选 → 创建类型2
原始类型1 + 未勾选／无权限              → 创建类型1
原始类型2                             → 创建类型2，不展示新入口
其他原始类型                           → 保留原值及原兜底分支
```

### 3.2 预览类型与读取

在 `EmployerOrderConfirmPreviewResult` 追加可选 `order`，其中 `canChangeOrderType?: boolean`。保留已有 `product: EmployerProductDetailResult`。可选声明用于兼容字段缺失，不代表前端放宽权限类型。

唯一放行判断：`res.data?.order?.canChangeOrderType === true`。缺失 order、缺字段、false、null、字符串或数字均按不支持处理。不新增 any 断言，不到 product 对象寻找同名字段，不查询标签。

### 3.3 接口消费表

| 请求 | 参数／出参处理 |
|---|---|
| confirm-preview | 路径和请求参数不变，新增读取 order 权限 |
| coupons/precalculate | 原 orderType、需求条件和其他参数不变；checkbox 不触发重新试算 |
| review-price | 原构造方法、watch 依赖和金额处理不变 |
| fulfillment-bond/match | 原 matchParams、规则匹配和异常策略不变；不接收新选择类型 |
| 创建 V2 订单 | 仅 orderType 改读 submittedOrderType；其他字段保留当前构造方式 |
| 合同／收银台 | 仍以创建结果的订单 ID 继续，不增加模式参数 |

不新增 `purchase_mode`、`canSelectPurchaseMode` 或伪造 `demandId`。直采切反采时 demandId 保持缺省。

## 四、页面进入与权限刷新

### 4.1 每次进入

- 全新实例的选择默认 false，权限默认 false，预览未就绪，订单 ID为空。
- 保留 mounted 拉取预览和现有 PV，不额外新增一套 immediate watch 导致双请求。
- F-03 仅改变确认页实例 key，同路径不同 query 会重新执行 setup/mounted，数量、商品、优惠券和弹窗自然进入新页面的原初始化流程。
- 离开再进入原 URL 同样是新确认过程；不会从历史状态恢复勾选。完全相同 URL 的重复 router.push 属于重复导航，不额外伪造一次进入。
- fullPath 也包含 hash；本页若发生 hash 变化同样重建。当前方案接受这一行为，不建立额外的购买参数缓存键。
- 服务大厅列表、IM、个人中心等其他页面的 key 和 keepAlive 行为不改变。

### 4.2 预览加载与失败刷新

每次 `fetchDetail()` 开始，将新选择、权限和预览就绪标记重置为 false；这也适用于创建失败后的原有刷新调用。

收到有效商品预览后，赋值 product 与严格布尔权限，标记预览有效，再按原调用链同步数量、拉优惠券和价格。`loading` 仍覆盖该加载过程。现有价格请求自己的失败策略保持，不新增因 checkbox 而触发的阻断或重试。

预览业务失败、商品失效、异常时，新权限和就绪状态保持关闭，沿用原提示与返回路径。即使画面还留有旧 product，也不能凭旧权限继续提交。

创建失败后再次刷新成功，即使仍获准切换，也回到未勾选；用户重试反采需要重新勾选。这是本方案对失败刷新周期的明确选择，待本轮整体验收，不冒充原型已规定的交互。

### 4.3 卸载与迟到结果

在 buy.vue 卸载前标记 `pageDisposed=true`，结束尚未完成的保证金等待（返回取消），清空 resolver。保留原有 PV 结束和 observer 释放。

在预览响应、用户信息补取、雇主功能校验、保证金匹配／确认、创建响应、合同简要状态等异步恢复点检查 pageDisposed，失效实例不继续发起创建、更新新权限、打开本页合同弹窗或执行本页跳转。nextTick／字体等待后的 observer 安装也要检查。

成功返回与异常 catch 都检查实例存活，避免旧请求抛错后仍执行失败刷新。首次用户信息补取异常沿用下单失败提示，并通过外层 finally 解锁。

在既有价格请求版本判定中补充实例存活条件，卸载时失效旧请求版本，避免旧实例继续刷新价格链；不改变价格参数或正常触发条件。

不宣称能够撤回已发出的创建请求。公共收银台内部异步及外部签署窗口的全局取消不在本次改造范围，不增加未经约定的取消接口。

## 五、UI 与组件设计

### 5.1 位置与文案

最终顺序：订单总价 → 优惠金额 → 实付价 → **原需付款行** → 模式选择卡片 → 原提交按钮 → 模式说明。

- 卡片标题：先签约后支付。
- 辅助文案：勾选后：先生成并签署合同，签署完成后再付款。
- 按钮下说明：提交后订单模式不可修改；本页每次进入均默认「直采」，不记忆上次选择。
- 卡片及这条说明都由 `showOrderTypeOption` 控制，已有需求链路不出现“默认直采”误导文案。
- 默认未勾选，支持键盘 Tab／空格及点击标签切换；点击辅助文案不额外重复翻转。
- 不新增外层 click 手动取反，与 Checkbox 的 `v-model:checked` 保持单一更新来源。
- 无权限不留空白卡片；不复制红框、原型演示开关或示例金额。

### 5.2 临时样式参数

以下是用于实施的临时数值，不声称来自正式设计稿的像素测量：

| 项目 | 方案值 |
|---|---|
| 卡片 | 宽度100%，box-sizing border-box，顶部间隔12px，内边距12px，边框1px，圆角8px |
| 未选 | 白底，边框 `#E8E8ED` |
| 选中 | 背景 `#F5F5FF`，边框复用页面 `@primary-color`（主题色回退值 `#5653F8`） |
| 主标题 | 14px，行高22px，颜色复用 `@text-primary` |
| 辅助文案 | 上间隔4px，12px，行高18px，复用 `@text-secondary`，可自然换行 |
| 按钮下说明 | 上间隔8px，12px，行高18px，复用 `@text-muted` |

新增 Less 嵌套在独立 `.order-type-option` 区域，不修改全局 Checkbox 主题，不影响现有金额字体与卡片布局。窄宽时文案换行，不固定卡片高度。正式 UI 后续另行更新。

### 5.3 禁用与已创建状态

- Checkbox 在 loading、submitting 或 currentOrderId 非空时禁用。
- 新建按钮在 submitting、loading、预览未就绪或无库存时禁用；handler 也做同等入口校验，不能只依赖 DOM disabled。
- 本页收到有效订单 ID 后，模式保持禁用；原提交按钮在本次异步完成后显示“查看订单”，点击复用 `EmployerMyOrderDetail` 路由与 currentOrderId，不再次创建。
- “查看订单”只受提交处理中限制，不因当前库存或新建预览条件阻止查看已有订单；创建失败无 ID时恢复原提交文案。
- 按钮文案优先级：submitting 显示“提交中...”，已有 ID显示“查看订单”，无库存显示“暂无库存”，其余显示“提交订单”；文案派生放脚本中，不在模板堆叠判断。
- 上述成功后按钮复用是防重复创建的恢复入口，属于方案新增交互，需本轮用户确认；不新增其他页面功能。

## 六、提交事务与后续流程

### 6.1 提交顺序

```text
正在提交 → 直接返回
已有有效订单ID → 查看该订单，不再进入创建
新建：保留环境开关、认证、商品、预览、库存等校验
→ 同步设置 submitting=true，记录 submittedOrderType
→ try 内补取用户信息，检查实例存活与雇主ID
→ 原提交埋点使用类型快照，保留原记录时机（身份就绪后、功能校验前）
→ 雇主功能校验
→ 原保证金匹配及选择
→ 若用户取消或页面失效：退出，不创建
→ 创建请求的 orderType 使用类型快照
→ 业务失败／异常／缺ID：原提示及刷新，不进成功分支
→ 保存 currentOrderId
→ 类型快照2：既有签约；类型快照1：既有零元／收银台；其他：原兜底
→ finally 统一释放 submitting
```

提交锁从补取用户信息前开始覆盖，不再在保证金弹窗前后反复释放。创建前不重新读取 checkbox；创建后也不重新计算可变状态来选分支。

当前保证金匹配参数构造和其他创建字段构造保持原位置与原口径。本方案只锁定新增模式，不借此改造数量、优惠券整表快照或价格重算规则。

### 6.2 保证金关闭与取消

在父页把 `requestBondConfirmation` 完成值扩展为 `boolean | null`：true=需要，false=不需要，null=取消本次提交。这是前端内部值，不是接口字段。

父页显式绑定 `:visible` 和 `@update:visible`，由 `handleBondVisibleChange` 更新可见性：关闭且还有待处理 resolver 时，清空 resolver 并完成为 null。原 `@confirm` 先完成 true／false 并清空 resolver；子组件随后关闭不会二次处理。

| 结果 | 处理 |
|---|---|
| true | 原保证金参数齐备时附加参数，继续创建 |
| false | 不附加保证金参数，继续创建 |
| null | 直接退出本次 handler，finally 解锁；保留当前 checkbox 选择供用户调整，不自动创建 |
| 匹配接口失败 | 保留原异常后继续创建策略，不把业务异常冒充用户取消 |

取消必须在宽泛的保证金 catch 之外被明确区分；不得抛一个通用异常后被原 catch 吞掉，进而继续下单。resolver 必须只完成一次。关闭、取消、再次提交均纳入验证。

### 6.3 成功分支与防重复创建

- 使用局部 `submittedOrderType` 替换原成功分支中的两处类型判断。
- 类型2调用既有 `handleSignContract(orderId)`，改为等待其请求处理结束再释放提交锁；不改变合同状态分支和子组件事件。
- 类型1保持原实际支付金额取值顺序、零元直采、待付阶段 ID和各支付结果处理。
- 一旦取得有效 currentOrderId，即使合同状态请求失败、收银台预检失败或支付失败，也不把“再次点击”变成第二次创建；由“查看订单”继续原订单。
- 不因为选择反采就自行触发支付；也不因为 URL 仍是1而打开直采收银台。

### 6.4 埋点与失败边界

- `trackOrderSubmitClick` 接收本次类型快照，`order_type` 仍按原要求转字符串。
- 本页支付曝光传入该快照；`fromQuery`、`payTypeQuery`、事件名、金额与保证金语义保持原口径。
- 不修改公共 tracking helper，也不写回 URL 以“修正来源”。
- 后端拒绝切换时沿用 `res.message` 和原失败刷新，不猜错误码；前端不自动以类型1重试创建。
- 网络超时无法证明服务端未创建成功；保留现有失败处理，不新增自动重试、幂等字段或后台查询协议。

## 七、保持不变与旧逻辑保留

1. 原始 `orderType` 定义、三个前置接口类型来源、请求字段、价格 watch 不替换为 createOrderType。
2. 原有需求入口保持类型2；已有需求 ID透传，不伪造新的需求上下文。
3. 保留库存、认证、数量、优惠券、价格、保证金匹配、零元支付、合同和支付结果业务规则。提交锁与取消收尾的局部变化见第六章，不将其描述成“保证金业务改了”。
4. 替换的旧表达式／绑定／锁切换就近注释保留，使用 `[REQ-170]` 说明实际原因；不复制整函数制造大块死代码。

## 十、风险与方案确认点

### 10.1 风险和适用边界

| 风险 | 处理／边界 |
|---|---|
| 公共布局误改全站 key | 仅匹配 EmployerPurchaseBuy；F-03 独立批次，V-14 回归 |
| 全程锁遇关闭悬挂 | null 取消结果、父页消费可见性事件、统一 finally；V-08 验证 |
| 勾选后创建2但试算仍为1 | 这是 server 已确认口径，不擅自“修正”；V-05 检查真实请求 |
| 已创建后继续签约／支付失败 | 复用 currentOrderId，提供查看已有订单入口，不再次创建 |
| 断网／离页时服务端结果未知 | 前端不保证幂等，不声称撤销；保持原失败策略，不新增协议 |
| 临时 UI 后续调整 | 样式局部化，正式稿只变样式可局部更新；业务交互变化需回退需求确认 |
| 源码基线更新 | 编码前重查 HEAD、工作区和目标 diff，不能覆盖用户的新改动 |

### 10.2 等待用户确认的方案选择

接口字段、checkbox 形态、三接口不改均已确认，不重复询问后端。当前等待的是以下具体技术方案验收：

1. 三个文件的改动范围，尤其确认页专属 key 对公共布局的局部调整。
2. 保证金关闭取消本次提交并解锁；需要／不需要仍按原规则继续。
3. 创建失败刷新后重置未选；创建成功留页时按钮复用为“查看订单”，不再次创建。
4. 保留需付款行，新增卡片置于其后；按第五章临时样式实施。

以上为推荐实施口径，全部明确，但尚未获准编码。若用户不接受其中任何项，先修订本方案；不默默换用备选方案。阶段3需用户另行明确授权，后续审查和测试阶段仍按工作流推进。
