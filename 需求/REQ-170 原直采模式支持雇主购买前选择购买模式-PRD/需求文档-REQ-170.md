## 二、目标与范围

### 2.1 需求目标

允许符合服务端条件的雇主，在原直采确认订单页勾选“先签约后支付”。未勾选保持既有直采流程；勾选后创建反采订单，并接入既有签约流程。

- 直采：先支付后签约。
- 反采：先签约后支付。
- 本需求新增直采入口选择反采的能力，不重建合同、支付或履约状态机。

### 2.2 本轮 Web 范围

| 范围 | 处理内容 |
|---|---|
| `ai-platform/es-web` 雇主端确认订单页 | 展示权限读取、checkbox、默认态与取消交互、创建订单类型、创建成功后的流程分支 |
| 确认预览响应类型 | 接入 `order.canChangeOrderType`，保留原商品数据 |
| 直采购买入口 | 覆盖服务大厅正常购买及对话中的直接购买；在共用确认页承接，不预设需要修改入口路由 |
| 既有需求购买链路 | 作为兼容与回归范围，保持原来的反采顺序，不新增模式切换入口 |
| 优惠券、价格、履约保证金 | 作为回归范围；server 已确认无需调整三个下单前接口 |

### 2.3 原始 PRD 的其他范围

原始 PRD 还列出 APP、服务商端、运营后台、订单列表及详情展示；其中列表与详情的详细 UI 方案带有删除线，与概述中的范围表述并不完全一致。

这些内容不自动转成本轮 Web 确认页的改动任务，也不在本文中宣称已经全局取消。后续若用户要求纳入，需重新确认需求范围，并按 workflow 回到相应阶段。订单列表、详情、合同和支付页面仍可纳入已有流程的回归检查，不等于新增展示或筛选功能。

后端标签管理、标签判定、二次校验、订单落库与状态机执行属于服务端职责；本轮前端不新增标签管理或标签查询能力。

## 四、场景与交互结果

| 场景 | 控件与选择 | 三个下单前接口 | 创建订单及成功后行为 |
|---|---|---|---|
| 原直采入口，接口允许切换，首次进入 | 展示，未勾选 | 保持原逻辑，入口类型为 `1` | 提交 `1`，沿用直采流程 |
| 原直采入口，接口允许切换，用户勾选 | 展示，已勾选 | 不因勾选改为 `2` | 提交 `2`，进入签约流程 |
| 原直采入口，勾选后取消 | 展示，未勾选 | 保持原逻辑 | 提交 `1`，恢复直采流程 |
| 原直采入口，接口不允许或字段缺失 | 不展示 | 保持原逻辑 | 提交 `1`，沿用直采流程 |
| 离开后再次进入原直采确认页 | 重新依据接口决定展示；选择回到未勾选 | 按原入口与页面初始化逻辑执行 | 不沿用上一次反采选择 |
| 既有需求购买链路，原始类型为 `2` | 不新增切换入口 | 保持该链路原逻辑与参数 | 保持 `2` 及原签约流程 |
| 创建订单被拒绝或请求失败 | 走失败处理；不把失败当作创建成功 | 不改变接口口径 | 不打开成功后的签约或支付流程 |

“默认直采”限定于原直采场景，不是对共用确认页所有来源强制赋值为 `1`。

## 五、接口与字段

### 5.1 确认预览

- server 文档地址：`gateway/aira-aiplatform-esp-api/v2/employer/orders/confirm-preview`。
- 新增字段：响应 `model.order.canChangeOrderType`，布尔值。
- 原商品数据仍位于 `model.product`。
- 前端请求封装后的读取路径须在阶段1核实，不能将字段误挂到 `product` 下。

server 响应业务部分：

```json
{
  "model": {
    "product": {},
    "order": {
      "canChangeOrderType": true
    }
  }
}
```

### 5.2 创建订单

- 复用既有 V2 创建订单接口及 `orderType` 入参，不新增购买模式字段。
- 原直采入口：未勾选为数字 `1`，勾选为数字 `2`。
- 创建成功后的签约／支付判断采用本次实际提交类型。
- 不将原始 PRD 的请求路径、`orderId` 示例或 `400x` 当成真实接口契约；实际封装与响应结构在阶段1复核。

### 5.3 明确保持不变的接口

| 接口用途 | 既有接口路径尾段 | 本轮约束 |
|---|---|---|
| 优惠券试算 | `coupons/precalculate` | 不因 checkbox 调整请求类型与需求上下文 |
| 价格复核 | `review-price` | 不因 checkbox 调整请求类型与价格计算口径 |
| 履约保证金匹配 | `fulfillment-bond/match` | 不因 checkbox 调整请求类型及匹配流程 |

server 已确认三个接口不需要改动，因此“它们是否需要传 `2` 并支持无 `demandId`”不再是待确认事项。其他原有触发条件仍按页面原逻辑执行。

## 八、异常与兼容边界

1. **新出参缺失或为 false**：原直采入口不开放反采。既有类型 `2` 的需求链路保持原行为。
2. **预览失败**：沿用页面既有加载与错误处理，不把失败解释为允许反采，也不绕过原有提交校验。
3. **下单权限二次校验失败**：按服务端失败响应提示并保留现有刷新处理。PRD 的提示为“当前账号不支持下单模式切换，请重新进入确认订单页”，不据此虚构错误码或替换所有错误提示。
4. **数据刷新后不再允许切换**：不得继续使用失效的反采选择；状态清理方式由阶段2明确。
5. **异步提交**：保证金确认等等待环节不能造成创建请求类型与成功后分支不一致；具体锁定方式由阶段2明确。
6. **既有流程**：保留原有登录、库存、数量、优惠券、价格和保证金校验，以及零元直采等原分支；不借需求切换顺手重构。
7. **无需求上下文的反采**：由直采入口的有效选择产生，不为满足旧路径而补造 `demandId`。
