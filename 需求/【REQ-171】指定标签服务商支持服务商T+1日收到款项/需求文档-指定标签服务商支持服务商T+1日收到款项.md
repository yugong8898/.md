## 1. 需求概述

对带有特定系统标签的高信用服务商的订单（下称 T+1 订单），本次前端仅实现两处 PC 端改动：

1. **雇主端-售后申请页**：T+1 订单售后类型屏蔽"退款""部分退款"，仅保留"返工"（且仅在验收通过阶段可发起售后）
2. **服务商端-订单详情页**：T+1 订单顶部新增特殊结算常驻提示

后端依赖：订单的 T+1 类型标识字段、售后创建接口的类型校验。

## 2. 需求规则清单（R-*）

| 编号 | 规则 | 来源 |
|---|---|---|
| R-101 | 触发条件：服务商关联特定系统标签（标签名称待业务确认），订单创建时判定订单类型；订单创建后服务商标签变更不影响已创建订单（不含总分包相关订单） | PRD 6.2.1 |
| R-102 | 售后申请页：T+1 订单售后类型仅展示"返工"选项，不展示"退款""部分退款"；选择返工后展示返工原因填写、返工说明、上传凭证等字段（现有返工流程） | PRD 6.4.3 |
| R-103 | 售后阶段状态规则（T+1 订单）：履约中→售后类型为空；待验收→空；验收通过→仅返工；验收不通过→空 | PRD 6.4.3 |
| R-104 | 异常拦截：T+1 订单通过 API/其他入口创建退款/部分退款售后时，后端返回错误码，前端提示"该订单不支持退款，仅支持返工" | PRD 6.4.3 |
| R-105 | 服务商端订单详情页：T+1 订单顶部展示提示"本订单为特殊结算订单，签约完成且雇主付款成功后款项次日到账。"常驻展示、不可关闭、仅 T+1 订单展示 | PRD 6.4.4 |
| R-106 | 回归约束：普通订单（非 T+1）售后类型展示与现状完全一致，不受本次改动影响 | PRD 6.4.3 对照表 |

## 4. 业务规则与边界条件

### 4.1 售后可选类型对照（核心规则）

**按阶段状态（T+1 订单屏蔽的依据）：**

| 阶段状态 | T+1 结算订单售后类型 | 普通订单售后类型（现状，不动） |
|---|---|---|
| 履约中 | **空** | 仅退款 |
| 待验收 | **空** | 仅退款 |
| 验收通过 | **仅返工** | 仅退款/仅返工 |
| 验收不通过 | **空** | 仅退款 |

**按支付/验收结构（PRD 补充）：**

| 场景 | T+1 结算订单 |
|---|---|
| 一次支付一次验收 | T+1 结算，不与验收结果挂钩，仅支持当前阶段售后 |
| 一次支付多次验收 | 同上，且不支持当前及剩余阶段售后 |
| 多次支付一次验收 | 同"一次支付一次验收" |
| 多次支付多次验收 | 同"一次支付多次验收" |

### 4.2 提示文案（仅服务商端，PRD 6.4.6 汇总表）

| 端 | 页面 | 文案 |
|---|---|---|
| 服务商端 | 订单详情页 | 本订单为特殊结算订单，签约完成且雇主付款成功后款项次日到账。 |

### 4.3 边界条件

1. T+1 订单在"履约中/待验收/验收不通过"阶段无任何售后选项（普通订单这些阶段有"仅退款"）——逆向屏蔽是本次核心，不能误伤普通订单
2. 订单创建后服务商取消标签 → 已创建订单仍按 T+1 逻辑展示
3. 打标前已产生订单 → 非T+1 订单，走现有售后逻辑
4. T+1 订单售后异常审核仅返工/驳回（运营后台逻辑，范围外，前端无需处理）

## 8. 影响范围

### 直接影响

- es-web：售后申请页（雇主视角）、订单详情页（服务商视角）

### 间接影响（回归风险点）

- 售后申请页：售后类型渲染若为多页面/多阶段共用逻辑，T+1 屏蔽不能误伤普通订单（R-106）
- 服务商端订单详情页：提示框插入不能影响现有布局
- 售后提交链路：拦截提示的展示方式与现有错误处理保持一致

## 9. 验证清单

```
□ T+1 订单售后：验收通过 → 仅"仅返工"选项（PC）
□ T+1 订单售后：履约中/待验收/验收不通过 → 无售后选项/入口（形态随 Q12 结论）
□ 普通订单售后：四阶段选项与现状一致（回归）
□ T+1 订单 API 提交退款售后 → 展示拦截提示
□ 服务商端订单详情：T+1 订单展示顶部常驻提示（PC）
□ 服务商端订单详情：普通订单不展示提示（回归）
□ 打标前订单（非 T+1）：售后与详情页均走原逻辑（回归）
```

## 10. 风险点

| 风险 | 说明 | 应对 |
|---|---|---|
| 售后选项屏蔽误伤普通订单 | 售后类型渲染若为共用逻辑，条件分支遗漏会删掉普通订单退款入口 | 阶段 2 重点设计；阶段 5 补普通订单回归用例 |
| 接口字段未定 | Q2/Q4 未定前只能占位实现 | 技术方案预留字段映射，确认后单点替换 |
| 售后入口形态不明 | "售后类型为空"的交互形态影响改动范围 | 阶段 1 看现状代码后定 |

## 11. 开发顺序建议

1. 阶段 1 代码分析：售后申请页现状（售后类型来源、入口控制）+ 服务商端订单详情页现状
2. 推动 Q2/Q4 后端确认（并行）
3. 阶段 2 技术方案 → 阶段 3 编码（服务商端提示先做，售后屏蔽后做）
