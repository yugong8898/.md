## 1. 背景与目标

二级频道配置页三个模块（内容运营模块 · 王新骏）均有图片上传诉求：

| 使用点 | 模块 | 必填条件 |
|---|---|---|
| 智能体封面图 | 智能体市场 | 选填 |
| 活动展示图片 | 活动专区 | 「展示活动 Banner」开启时必填 |
| 文章封面图 | 行业资讯 | 必填 |

统一口径（来自《二级频道页-工作清单》1.3 关键约定）：

- 格式：PNG / JPG / JPEG（**不含 GIF**，注意与营销位素材口径不同）；
- 大小：单张 ≤ 20480KB（即 20MB；组件层按 KB 设计）；
- 上传中展示 loading；上传成功预览；失败 / 未传展示缺省态；
- 支持替换与删除；
- 支持只读模式（配合模块 `index.vue` 的 `readonly` prop）。

**目标**：抽一个与业务解耦的统一图片上传组件（工作清单定名 `ChannelImageUpload`），三模块统一使用，模块内不各自实现上传逻辑；后续其他模块（如汪明刚的 Banner 模块）也可按需接入。

**动态约束能力**：

- **格式动态**：允许格式由调用方以格式 key 数组传入，经常量映射表展开为 accept / 白名单校验 / 提示文案（不写死）；
- **大小动态**：大小上限由调用方传入，**单位 KB**（如 20480KB = 20MB）；
- **尺寸 / 比例限制**：支持「固定像素尺寸（严格 / 宽松）」「宽高比 + 最小宽高」三类客户端前置校验，不合规直接拦截不上传；「建议尺寸」为软提示，不拦截。

**实现总原则：el-upload 原生优先**——文件选择、校验拦截、上传执行、失败处理尽量挂 el-upload 原生钩子（`before-upload` / `http-request`），自研逻辑只保留 el-upload 覆盖不了的部分（校验链内容、缩略图视觉、只读态、加载失败缺省）。

## 2. 现状盘点

> 以下为横向搜索后的既有事实，方案全部建立在此之上。

| # | 既有资产 | 位置 | 说明 |
|---|---|---|---|

| 3 | `ImageCropperDialog` | `src/pages/marketing-position/components/ImageCropperDialog/` | 基于 `vue-cropper`，纯裁剪不上传，API 通用（`aspectRatio` / `accept` / `maxSizeMb` 均可配），有 README |
| 4 | `ImagePreviewViewer` | `src/pages/marketing-position/components/ImagePreviewViewer/` | 全屏预览 / 缩放 / 旋转 / 下载 / 可选删除，Teleport 到 body（z-index 4000），有 README |
| 5 | 营销位常量口径 | `marketing-position/constants.ts` | `MATERIAL_IMAGE_ACCEPT` 含 GIF、`MAX_SIZE_MB = 20`、`businessId='esp'`、`businessType='114'` |

**与营销位方案的差异点**（决定不能直接搬 `MaterialImageUpload`）：

1. 二级频道三处图片**需求未要求裁剪**，营销位是强制裁剪流程；
2. 格式口径不同（不含 GIF）；
3. 营销位组件挂在页面目录下，跨页面引用违反分层，且常量写死营销位业务标识；
4. 二级频道需要 `readonly` 只读模式，营销位组件没有。

## 3. 设计决策

### 3.1 组件定位与放置

**组件名**：`ChannelImageUpload`（单图、URL 字符串绑定；命名对齐《二级频道页-工作清单》）。

**放置位置**：`src/pages/secondary-channel/components/ChannelImageUpload/`（本方案推荐）

- 该目录已存在且现挂 `CreateChannelDialog.vue`（频道列表页与表单页共用的组件），与「二级频道内多页面共用」的定位一致；
- 决策理由：本期改动收敛在工作边界内，不动全局 `src/components/`；三模块的弹窗/卡片均可直接引用；
- 与工作清单的差异（见第 9 章待确认 #14）：工作清单暂定 `form/components/ChannelImageUpload.vue`（单文件，目录约定与张立对齐后可调整）；本方案推荐目录式落位（四文件结构，见 3.5）。两口径**命名一致、仅落位层级不同**，动手前与张立对齐一次，以对齐结果为准；
- 演进预案：未来若出现二级频道外的第二个消费方（如汪明刚的 Banner 模块），再整体上移至 `src/components/` 并批量替换引用路径——组件本身无页面专属逻辑，上移成本仅为改 import 路径。

### 3.2 裁剪 / 预览子组件的依赖处理

`ImageCropperDialog` 与 `ImagePreviewViewer` 目前挂在 `src/pages/marketing-position/components/` 下：

- **预览**是必选依赖 → 必须解决跨页面引用问题；
- **裁剪**二级频道本期不需要 → 做成可选能力（`croppable` prop，默认 `false`）。

**处理方案：不动，跨模块直接引用**

- `ImagePreviewViewer` / `ImageCropperDialog` 均保留在营销位目录，不上移、不复制；
- 本组件直接跨模块 `import` `ImagePreviewViewer`（预览必选），引用处附 `TODO: wxj` 标注分层债务，待未来出现第二个消费方时再统一上移全局；
- `ImageCropperDialog` 本期不用（不裁剪），不引入引用，保留给未来 `croppable` 需求。

### 3.3 数据契约（单图）

与既有 `MaterialImageUpload` 保持一致，降低团队理解成本：

- `defineModel<string>`：绑定 OSS 返回的 `url` 字符串（空字符串 = 未上传）；
- 上传成功后组件内部完成 `modelValue` 写入，`submit.ts` 取数不变；
- **单图定位**：不引入多图能力——二级频道三处均为单图槽位，多图场景另起容器组件，避免模型分裂（`string` vs `string[]`）；多图扩展预案见 3.4。

### 3.4 多图支持预案（本期不落地）

**结论：不做「一个组件兼顾单/多图」，多图需求出现时用独立容器组件承接；基于 el-upload 原生 `fileList` 模式，容器实现为薄封装。**

不采纳单/多图同体模式的理由：

- 兼顾单/多图会被迫按数量返回不同形态的值，返回值形态分裂；
- `v-model` 类型会在 `string` 与 `string[]` 间分裂，各模块 `validate.ts` 取数、只读展示、表单回填全部分叉；
- 当前需求面全是单图槽位（三模块封面/展示图 + 汪明刚 Banner 每 Banner 一张），无多图点位。

组合式分层（实现路径）：

```
ChannelImageUpload（原子组件，单图，v-model: string）  ← 本期交付
    共享校验链（validators）+ customRequest
ImageUploadGroup（多图容器，v-model: string[]）    ← 预留设计，不开发
    = el-upload :limit=N + fileList 数组直接映射
    + 同一套 validators 挂 before-upload + 同一套 customRequest
```

- 单图调用方永远拿 `string`，多图调用方拿 `string[]`，模型永不分裂；
- 深度复用 el-upload 后，`ImageUploadGroup` 走 `fileList` 数组原生模式（而非 N 个单图实例拼装），比「实例编排」更薄；
- 多图容器使用 `:limit` 时**必须**在校验失败分支 `clearFiles()` 清残留（见 3.6 契约要点，防被拦截文件占配额）；
- 本期不为不存在的需求写代码，仅留实现路径预案。

### 3.5 可维护性与扩展设计（逻辑层 / 视图层分离）

目录结构：

```
src/pages/secondary-channel/components/ChannelImageUpload/
├── use-image-upload.ts   # 逻辑层：纯函数校验链（格式→大小→尺寸/比例，管道式可插拔）+ customRequest 上传 + el-upload 钩子接线
├── constants.ts          # IMAGE_FORMAT_MAP 等（见 4.2）
├── index.vue             # 视图层：el-upload 钩子绑定 + 缩略图/触发区渲染编排，不写校验/上传逻辑
└── README.md             # 组件手册（Props/事件/示例），对齐 ImageCropperDialog / ImagePreviewViewer 既有惯例
```

扩展路径：

- **横向（新文件类型）**：未来做 `FileUpload`（附件）/ `VideoUpload` 时，将 `use-image-upload` 中的校验链与上传调用上抽为公共 `use-oss-upload`，逻辑复用、视图各自实现，不重复抄校验代码；
- **纵向（新校验规则）**：校验链为独立纯函数步骤（格式 → 大小 → 尺寸/比例），新增规则（如最小尺寸、最长边限制）只加一个 validator，不动主流程；
- **格式扩展**：`IMAGE_FORMAT_MAP` 加行即可支持新格式（如 webp），组件逻辑零改动；
- **交付物**：README 与组件同交付，用法/约束/示例一次性写清，降低后续接入沟通成本。

### 3.6 `use-image-upload.ts` 对外契约

逻辑层 composable 是视图层与校验/上传之间的**唯一桥梁**，签名定案如下（开发时不得再二次设计）：

```ts
// use-image-upload.ts
export function useImageUpload(
  props: ChannelImageUploadProps,   // 组件 props（reactive 对象直接传入，禁止解构，避免丢响应性）
  emit: ChannelImageUploadEmit,     // ('update:modelValue' | 'change' | 'success' | 'error', ...args)
) {
  return {
    // —— el-upload 钩子接线 ——
    beforeUpload,     // (rawFile: File) => Promise<boolean>  挂 :before-upload；跑完整校验链，返回 false 拦截不上传；失败分支清残留（见契约要点）
    customRequest,    // (options: UploadRequestOptions) => Promise<void>  挂 :http-request；调 uploadWithOriginalName，成功写值并 emit，失败 ElMessage + emit('error')
    uploadRef,        // Ref<UploadInstance | undefined>  绑 el-upload ref，供校验失败分支 clearFiles()
    // —— 状态（暴露给视图层绑定） ——
    uploading,        // Ref<boolean>  customRequest 开始置位 / finally 复位；驱动 v-loading 与禁用
    previewVisible,   // Ref<boolean>  全屏预览弹层显隐（v-model 给 ImagePreviewViewer）
    imageError,       // Ref<boolean>  缩略图加载失败标记（缺省占位用）
    acceptAttr,       // ComputedRef<string>  由 formats 经 IMAGE_FORMAT_MAP 展开
    tipText,          // ComputedRef<string>  次级文案「PNG / JPG / JPEG, ≤20MB」
    recommendText,    // ComputedRef<string>  「建议 W×H」（仅 dimensions mode='recommend' 时非空）
    // —— 方法 ——
    remove,           // () => void  删除（缩略图删除按钮与预览内删除共用）：写空值 + emit('change')
    openPreview,      // () => void  打开全屏预览（置 previewVisible = true）
  };
}
```

契约要点：

- **校验链为纯函数**（管道式，见 3.5），挂载在 `before-upload`：格式 → 大小 → 尺寸/比例，任一失败返回 `false`；纯函数形态保证未来 `ImageUploadGroup` 原样复用；
- **上传挂载在 `http-request`**：不使用 el-upload 的 `action`，内部调 `uploadWithOriginalName`；成功提取 `url` 校验合法后 `emit('update:modelValue')` + `success` + `change`；
- **校验失败必清残留**：`before-upload` 返回 `false` 时，被拦截的文件可能在 el-upload 内部 `uploadFiles` 残留，须 `nextTick(() => uploadRef.value?.clearFiles())`，防止后续选择被干扰（多图容器用 `:limit` 时此为刚需）；
- **单图靠结构性保证，不用 `:limit`**：`modelValue` 有值时触发区整体替换为缩略图（`el-upload` 与缩略图不共存），天然单图；避开 `:limit` 与拦截残留文件的配额占用陷阱；
- **`uploading` 最小化自维护**：仅 `customRequest` 前置位 / `finally` 复位，用途只有 `v-loading` 与禁用；不引入独立上传状态机；
- 视图层（`index.vue`）**不直接**调用 `uploadWithOriginalName`、不拼任何校验文案，全部经由 composable；
- `croppable` 开启时，`beforeUpload` 内先弹 `ImageCropperDialog` 拿裁剪产物再走校验链尾段（本期 `croppable` 恒 `false`，代码留分支不启用）。

### 3.7 el-upload 能力复用边界

**原则：上传链路全走原生钩子，展示层按原型与先例自绘。**

复用（挂载点）：

| 能力 | el-upload 挂载点 | 说明 |
|---|---|---|
| 文件选择 + 同名重选 | 组件本体（`auto-upload` 由钩子接管流程） | `input` 重置由 el-upload 内部处理 |
| `accept` / `disabled` | 原生 props | `acceptAttr` 由映射表展开 |
| 校验拦截 | `:before-upload` | 异步，返回 `false` 即不发起上传 |
| 上传执行 + 失败处理 | `:http-request` | 接 `uploadWithOriginalName`，reject 即失败 |
| 触发区点击交互 | 默认插槽 | 原型三行式卡片放插槽内（见 4.4） |

**不采纳的三项（含理由）**：

1. **不用 `list-type="picture-card"`**：原型视觉为「缩略图 + 右上角删除按钮」（营销位先例同款），picture-card 的 hover 蒙层式还原不了；且其内部 `<img>` 无 error 钩子，「加载失败缺省态」无法接管。**缩略图层 `show-file-list=false` + 组件自绘**（与先例一致，imageError 可控）；
2. **不用 `:limit`**：单图由「有值即换缩略图」的结构性互斥保证（见 3.6）；`:limit` 在存在拦截残留文件时有配额占用陷阱，留给多图容器场景并配套 `clearFiles()`；
3. **只读态不走 el-upload**：el-upload 无 `readonly`，只读时直接不渲染 el-upload，纯展示缩略图 + 点击预览（见 5.5）。

实现要点：

- `on-change` 不参与流程（校验/上传全部由 `before-upload` + `http-request` 承接），不自维护文件选择回调；
- 上传中 el-upload 绑 `:disabled="uploading"`（与 `disabled` prop 叠加），防止重开选择框。

## 4. 组件 API 设计

### 4.1 Props

| 属性 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `modelValue` | `string` | `''` | 图片 URL，`v-model` 绑定；空串表示未上传 |
| `readonly` | `boolean` | `false` | 只读模式：仅展示缩略图 + 点击预览，隐藏上传/删除/替换 |
| `disabled` | `boolean` | `false` | 禁用编辑态（如模块禁用时），仍展示已有图 |
| `title` | `string` | `'上传图片'` | 触发区主文案，**按槽位定制**（原型：「上传活动图片」/「上传文章封面图」/「上传智能体封面图」） |
| `formats` | `ImageFormatKey[]` | `['png','jpg','jpeg']` | **格式动态**：格式 key 数组（映射关系见 4.2 格式映射常量）；组件据此展开原生选择框 `accept`、运行时白名单校验、提示文案三件事；二级频道默认口径不含 GIF |
| `maxSizeKb` | `number` | `1024` | **大小动态**：大小上限，**单位 KB**；默认 1024KB（=1MB），二级频道槽位按需传 20480（=20MB） |
| `dimensions` | `{ width: number; height: number; mode?: 'recommend' \| 'max' \| 'strict' }` | 不传 = 不校验 | **像素尺寸限制**：`mode='max'`（缺省）宽、高均不超过 W×H；`mode='strict'` 必须恰好等于 W×H；`mode='recommend'` 仅软提示（展示「建议 W×H」，不拦截上传） |
| `ratio` | `{ w: number; h: number; minWidth?: number; minHeight?: number }` | 不传 = 不校验 | **宽高比限制**：图片宽高比必须为 `w:h`；可选附最小宽/最小高（与比例同时校验） |
| `triggerSize` | `number` | `100` | 上传框 / 预览框边长（px） |
| `tip` | `string` | 按 formats / maxSizeKb 自动生成 | 触发区次级文案，格式「{格式清单}, ≤{大小}」（原型：「PNG / JPG / JPEG, ≤20MB」）；内部口径为 `maxSizeKb`，展示层折算 MB；尺寸建议行由 `dimensions`（`mode='recommend'`）生成 |
| `required` | `boolean` | `false` | 是否必填（仅展示红星标识，校验交给模块 `validate.ts`） |
| `croppable` | `boolean` | `false` | 是否走裁剪流程；开启后需传 `aspectRatio` |
| `aspectRatio` | `readonly [number, number]` | `[4, 3]` | 裁剪宽高比，仅 `croppable` 时生效 |
| `businessId` | `string` | `'esp'` | OSS 业务标识，透传上传接口 |
| `businessType` | `string` | 占位值（`TODO: wxj`） | OSS 业务类型，后端给值后替换（见风险点 #2）；**不借用营销位的 `'114'`** |
| `previewFilename` | `string` | `'image'` | 预览下载时的文件名 |
| `extraFormData` | `Record<string, string>` | `{}` | **预留扩展位**：当前 `uploadWithOriginalName` 仅支持 `businessId` / `businessType` / `originalFileName`，无附加参数通道，故**暂不随请求发送**（`TODO: wxj`，接口扩展后接入）；保留 prop 占位以免后续破坏 API |

### 4.2 格式映射常量（与组件同目录 `constants.ts` 维护）

格式约束的**单一事实源**：`accept` 拼接、白名单校验、提示文案均由映射表展开，新增格式只改常量不动组件逻辑：

```ts
// constants.ts
export const IMAGE_FORMAT_MAP = {
  png:  { mime: 'image/png',  ext: '.png',  accept: 'image/png,.png',   label: 'PNG' },
  jpg:  { mime: 'image/jpeg', ext: '.jpg',  accept: 'image/jpeg,.jpg',  label: 'JPG' },
  jpeg: { mime: 'image/jpeg', ext: '.jpeg', accept: 'image/jpeg,.jpeg', label: 'JPEG' },
  gif:  { mime: 'image/gif',  ext: '.gif',  accept: 'image/gif,.gif',   label: 'GIF' },
} as const;

export type ImageFormatKey = keyof typeof IMAGE_FORMAT_MAP;

/** 二级频道默认口径（不含 GIF） */
export const SECONDARY_CHANNEL_DEFAULT_FORMATS: ImageFormatKey[] = ['png', 'jpg', 'jpeg'];
```

展开规则：

- `accept` = `formats.map(k => IMAGE_FORMAT_MAP[k].accept).join(',')`；
- 白名单 = 映射项 `mime` + `ext` 的集合，校验时 `file.type` 与文件名后缀**双判断**（用户可选「所有文件」绕过原生 accept）；
- 提示文案 = 「支持 」+ `formats` 各项 `label` 顿号拼接；
- 组件内部不出现任何写死的格式字符串；映射表需要新增格式（如 webp）时，只加常量项即可。

### 4.3 Events

| 事件 | 参数 | 说明 |
|---|---|---|
| `update:modelValue` | `value: string` | v-model 内置；上传成功写入 URL、删除清空 |
| `change` | — | 值变化（上传成功 / 删除）后触发，供调用方做联动 |
| `success` | `result: { url, ossCode?, fileName? }` | 上传成功，供需要 `ossCode` 的场景 |
| `error` | `error: Error` | 校验失败或上传失败（组件已 `ElMessage.error` 提示，事件仅供调用方额外处理） |

### 4.4 Slots

| 插槽 | 说明 |
|---|---|
| `trigger` | 完全自定义上传触发区（内容同样渲染在 `el-upload` 默认插槽内，选择文件交互仍由 el-upload 接管）；不传时走下方默认样式 |

**默认触发区规范（按原型还原）**：

- 实现：触发区整体作为 `el-upload` 默认插槽，点击选择文件由 el-upload 接管（校验/上传走 `before-upload` / `http-request`，见 3.6/3.7）；
- 结构：虚线圆角卡片（浅灰底），内部垂直居中三行式：图片图标（灰色线条 icon）→ 主文案 `title`（深色）→ 次级文案 `tip`（浅灰小字）；
- 次级文案格式：`{labels 以 " / " 拼接}, ≤{大小}`，如「PNG / JPG / JPEG, ≤20MB」（内部 `maxSizeKb` 整除 1024 折算展示；不能整除时保留一位小数）；
- 传了 `dimensions`（`mode='recommend'`）时，主文案区展示「建议 {W}×{H}」（可与 `title` 并存：`title` 为主、建议尺寸为附行）；
- 三处槽位对应传值：活动专区 `title="上传活动图片"`、行业资讯 `title="上传文章封面图"`、智能体市场 `title="上传智能体封面图"`（或「建议 400×300」形态，以产品定稿为准）。

### 4.5 内部职责边界

组件**只负责**：文件选择（el-upload）→ 校验拦截（before-upload）→ 上传（http-request → `uploadWithOriginalName`）→ 写值 → 预览/删除交互 → 只读展示。

组件**不负责**：业务必填校验（归各模块 `validate.ts`）、删除的业务二次确认（调用方处理）、列表回显数据组装。

## 5. 交互与状态设计

### 5.1 状态机

| 状态 | 条件 | 展示 |
|---|---|---|
| 空态 | `modelValue` 为空且非只读 | 上传触发框（`trigger` 插槽/默认样式，`el-upload` 承接点击） |
| 上传中 | `customRequest` 执行期间（`uploading = true`） | 触发框上 `v-loading`，`el-upload` 绑 `:disabled="uploading"` 禁止重复选择 |
| 预览态 | `modelValue` 有值且非只读 | 缩略图（contain）+ 右上角删除按钮 + 点击缩略图打开全屏预览（预览内含删除，删除后回空态重传）；此时 `el-upload` 不渲染（结构性单图，见 3.6） |
| 只读态 | `readonly = true` | 缩略图 + 点击预览；无删除、无上传入口；空值展示「暂无图片」缺省；不渲染 `el-upload` |
| 加载失败 | 缩略图 `<img>` `@error` | 缺省占位（图标 + 「图片加载失败」），编辑态提供重新上传入口 |

### 5.2 主流程

```
选择文件（el-upload 默认插槽点击）
  ↓
:before-upload 跑校验链（任一失败 → ElMessage.error + emit('error') + return false + clearFiles 清残留）
  ├─ 格式校验（formats 映射白名单：file.type + 扩展名双判断）「仅支持 PNG、JPG、JPEG 格式」（动态）
  ├─ 大小校验（≤ maxSizeKb，内部 KB、文案折算 MB）「图片大小不能超过 20MB」
  └─ dimensions / ratio 有传且非 recommend → 读真实宽高（见 5.4 实现要点）逐项校验：
       ├─ 图片解码失败（onerror）──→ 「图片文件无法解析，请重新选择」
       ├─ 严格尺寸不等 ──→ 「请上传 W×H 尺寸的图片！」
       ├─ 超宽松尺寸 ──→ 「请上传 W×H 尺寸以内的图片！」
       ├─ 低于最小宽/高 ──→ 「请上传不低于 minW×minH（w:h）的图片！」
       └─ 宽高比不符 ──→ 「请上传宽高比为 w:h 的图片！」
  ↓ return true
croppable ? 打开 ImageCropperDialog → 确认裁剪出 File : 直接用原 File
  ↓
:http-request → uploading = true，调 uploadWithOriginalName（extraFormData 为预留位、当前不随请求发送，见 4.1）
  ↓
返回 url 合法（http/https 开头）?
  ├─ 是 → emit update:modelValue = url，emit success/change（缩略图态自动切换）
  └─ 否 → ElMessage.error（取接口 message），emit error
  ↓
finally：uploading = false
```

### 5.3 关键交互约定

- **替换**：沿用营销位模式——预览态点击缩略图 → 打开 `ImagePreviewViewer`（`show-delete` 开启、`@delete` 走 composable 的 `remove()`），预览内删除后回空态重传，**单一入口**，缩略图不设「替换」按钮；
- **删除**：编辑态删除不弹二次确认（组件级），是否加确认由各模块调用方决定（行业资讯/活动专区工作清单中删除确认归模块交互）；只读态无删除；
- **并发防抖**：`uploading` 期间禁用触发框与删除按钮（沿用 `MaterialImageUpload` 既有写法）；
- **裁剪产物二次校验**：`croppable` 开启时，裁剪后 File 需再校验大小 ≤ `maxSizeKb`（`ImageCropperDialog` 只校验源文件，README 明确提示；其 `maxSizeMb` 入参由组件内部按 `maxSizeKb / 1024` 折算传入）；若同时传了 `dimensions`/`ratio`，裁剪产物也要复检（裁剪弹窗已按比例约束时可不重复）。

### 5.4 尺寸/比例校验实现要点

- 读取真实宽高：`URL.createObjectURL(file)` + `new Image()` 的 `onload` 读 `naturalWidth/naturalHeight`（不转 base64，大图友好）；
- 校验完成后必须 `URL.revokeObjectURL` 释放，含异常路径；
- 校验用 Promise 包装，`reject(文案)` → 调用点统一 `ElMessage.error`；
- 顺序：格式 → 大小 → 尺寸/比例（前两项不过不读图，省开销）；
- 严格尺寸比较用 `!==`（等于才算过）；比例比较用交叉相乘 `w * imgH === h * imgW` 避免浮点误差；
- **解码失败路径**：损坏文件 / 非图片伪装后缀会走 `Image` 的 `onerror` 而非 `onload`——该路径按**校验失败拦截**处理，文案「图片文件无法解析，请重新选择」，`emit('error')` 且终止；`onerror` 分支同样必须先 `revokeObjectURL` 再返回。

### 5.5 只读模式（对齐模块 `readonly` 方案）

- 三个模块 `index.vue` 收到 `readonly` prop 后，透传给所有 `ImageUpload` 实例；
- 只读态不渲染 `el-upload`，纯展示缩略图 + 点击放大预览（详情页核心诉求），隐藏一切写操作；
- 空值不做必填红标，展示缺省占位。

## 6. 校验规则

| # | 校验点 | 时机 | 提示文案（按入参动态生成） |
|---|---|---|---|
| 1 | 文件格式 ∈ `formats` 映射白名单（`file.type` + 扩展名双判断） | `before-upload`（上传前） | 「仅支持 PNG、JPG、JPEG 格式」（映射表 label 拼接） |
| 2 | 文件大小 ≤ `maxSizeKb`（内部单位 KB，文案展示折算 MB） | `before-upload`（上传前） | 「图片大小不能超过 20MB」 |
| — | 图片可解码（`Image` `onload` 正常触发；`onerror` 视为失败） | 读图时（仅需读图的校验项触发） | 「图片文件无法解析，请重新选择」 |
| 3 | `dimensions` `mode='strict'`：宽高恰好等于 W×H | 读图后、上传前 | 「请上传 1200×600 尺寸的图片！」 |
| 4 | `dimensions` `mode='max'`（缺省）：宽高均不超过 W×H | 读图后、上传前 | 「请上传 1200×600 尺寸以内的图片！」 |
| 5 | 最小宽/高：不低于 `ratio.minWidth × minHeight` | 读图后、上传前 | 「请上传不低于 800×400（2:1）的图片！」 |
| 6 | 宽高比：等于 `ratio.w : ratio.h` | 读图后、上传前 | 「请上传宽高比为 2:1 的图片！」 |
| — | `dimensions` `mode='recommend'`：仅触发区展示「建议 W×H」，不校验不拦截 | — | — |
| 7 | 裁剪后大小 ≤ `maxSizeKb` | 裁剪确认后、上传前（仅 `croppable`） | 「裁剪后图片超过 20MB，请重新调整」 |
| 8 | 接口返回 url 为合法 http/https | `http-request` 返回后 | 「上传失败：未返回有效的图片地址」 |
| 9 | 业务必填（如资讯封面、活动展示图片） | 提交审核时 | 归各模块 `validate.ts`，组件不拦截 |

> 格式校验**不能只信 `accept`**（用户可选「所有文件」），须用 `file.type` + 扩展名双判断，白名单数据源为 `IMAGE_FORMAT_MAP`，沿用 `ImageCropperDialog` 的校验实现思路。
