## 阶段6新暴露问题

### P6：settlementMode 消费点遗漏——合同确认页

**问题描述**：阶段1代码分析横向搜索 settlementMode 时，只命中了雇主售后、服务商详情和 3 处 types.ts。阶段6联调发现**合同确认页**（`contract/common.vue`）也需要根据 settlementMode 切换验收说明文案——T+1 订单不展示"验收通过后一次性结清尾款"。

**代码证据**：
```typescript
// ef8753351 src/views/employer/contract/common.vue L361-363
const isTPlusOneOrder = contractInfo.value?.settlementMode === 2
if (isTPlusOneOrder) return '全部服务完成后进行统一验收。'
```

**根因分析**（三层递进）：
1. **直接原因**：grep settlementMode 零命中 → 判定该页面不涉及。但合同确认页在阶段3编码时尚未消费该字段（后端尚未在合同接口下发），grep 自然找不到。
2. **深层原因**：横向搜索只做了"现有代码中谁在用这个字段"，没做"哪些页面在业务上需要这个信息"。合同确认页展示结算相关文案，属于可预见的消费场景。
3. **系统原因**：阶段1代码分析的横向搜索方法论存在盲区——**按字段名搜索只能发现已实现的消费点，无法发现尚未实现但业务上必然需要的消费点**。

**影响**：阶段6新增 1 笔提交（ef8753351），涉及 2 个文件（types.ts + common.vue）。

**改进措施**：新字段横向搜索须双轨并行——① grep 现有代码找已实现消费点；② 按业务语义推演潜在消费点（"哪些页面展示与该字段相关的信息？"）。

### P7：售后提交参数的条件性省略——PRD 未描述的接口约束

**问题描述**：`after-sale-apply.vue` 的 `handleSubmit()` 中，`orderStageScopeType` 参数在 T+1 场景下不应传值。这个规则在 PRD、阶段0需求文档、阶段2技术方案中均未提及，是联调时后端反馈才补上的。

**代码证据**：
```typescript
// d95d67c32 src/views/employer/order/after-sale-apply.vue L690-694
let orderStageScopeType: number | undefined
// REQ-171 T+1 特殊结算订单：后端不接受此参数
if (isTPlusOneOrder.value) {
  orderStageScopeType = undefined
} else if (fulfillmentMode.value === FulfillmentModeEnum.STAGED_PAY_ONCE_ACCEPT) {
```

**根因分析**（三层递进）：
1. **直接原因**：PRD 只描述了"T+1 订单售后可选项受限"，没有描述"提交参数也要变"。
2. **深层原因**：接口契约确认只覆盖了字段名/类型/层级三件套，没有覆盖**参数的条件性省略**——即"某个已有参数在新场景下不应传值"。
3. **系统原因**：这与第一轮复盘的"根因1（接口契约未书面确认就落地）"同源，但维度不同。第一轮关注的是"新字段的定义"，本轮暴露的是"旧参数在新条件下的行为变化"。两者合在一起才是完整的接口契约。

**影响**：阶段6新增 1 笔提交（d95d67c32），涉及 1 个文件（after-sale-apply.vue），6+/3-。

**改进措施**：接口契约确认从三件套扩展为四件套：字段名 / 类型 / 嵌套层级 / **旧参数的条件性行为变化**。

## 阶段6改动的纵深分析

阶段6的两笔修复虽然代码量小（合计 15+/3-），但揭示了两个不同维度的前期分析盲区。把它们放在一起看，可以发现一个模式：

| 维度 | P6 合同页遗漏 | P7 参数条件性省略 |
|------|-------------|-----------------|
| 遗漏类型 | 新消费点未发现 | 旧参数新行为未确认 |
| 搜索方法失效 | grep 字段名 → 零命中 ≠ 不涉及 | PRD 描述功能 → 未提及参数约束 |
| 前期可预防性 | 中（需业务语义推演） | 低（需后端主动告知或联调发现） |
| 修复成本 | 低（2文件9行） | 低（1文件6行） |
| 如果晚发现的成本 | 中（上线后文案错误） | 高（提交售后报错，阻断核心流程） |

**关键洞察**：P7 的风险远高于 P6，但前期可预防性反而更低。这说明**有些问题只能在联调中发现**，workflow 的目标不是消灭所有联调问题，而是确保联调发现的问题都是"低成本修复"的——从这个标准看，REQ-171 阶段6的两个问题都在可控范围内。

## 两轮复盘问题收敛：从10个事件到5个系统缺陷

第一轮识别 5 个问题（P1~P5），第二轮新增 2 个（P6~P7），合计 7 个事件。收敛为系统缺陷：

| 系统缺陷 | 覆盖的事件 | 两轮表现 |
|---------|-----------|---------|
| D1 接口契约确认不完整 | P1(字段名3轮)、P7(参数条件性省略) | 第一轮只关注新字段定义，第二轮暴露旧参数新行为 |
| D2 验证绿灯≠功能正确 | P4(ESLint假通过)、第一轮层级错配 | 第一轮工具层面，第二轮业务层面 |
| D3 审查锚点选错 | 第一轮CodeReview漏检KeepAlive、层级错配 | 审文档不审现实 |
| D4 UI组件选型未先比对 | P5(FriendlyTipModal→ConfirmActionModal)、第一轮a-alert返工 | 两个需求犯同一个错 |
| D5 横向搜索只有grep一个维度 | P6(合同页遗漏) | 第二轮新暴露 |

**D1 是最顽固的缺陷**：两轮复盘都触发了它的不同侧面。第一轮是"字段名/类型猜错"，第二轮是"旧参数在新场景下的行为没确认"。即使第一轮已经把"三件套确认"列为改进建议，第二轮仍然暴露了第四件套的缺失。这说明**接口契约的完整性不是一个可以一次性穷举的清单，而是一个需要在每次联调中持续补充的认知**。
