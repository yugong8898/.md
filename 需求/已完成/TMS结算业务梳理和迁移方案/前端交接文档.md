## 一、背景

后端将 TMS 结算模块（客户汇总、客户对账单、日常收入、日常支出、在途费用）从撮合结算链路解耦，新建 `tms-orch-settlement` / `tms-core-settlement` / `tms-base-settlement` 三层服务。

| 维度 | 迁移前 | 迁移后 |
|------|--------|--------|
| 接口前缀 | `/lmt-user/*`（撮合结算链路） | `/tms-settlement/*`（TMS 独立结算链路） |
| 后端服务 | `lmt-orch-user` / `lmt-core-settlement` / `lgi-base-settlement` / `BMS` | `tms-orch-settlement` / `tms-core-settlement` / `tms-base-settlement`（BMS 暂不拆） |
| 数据库 | 共用 BMS 数据库 | 暂不拆分，仍共用 |
| 前端策略 | — | **接口级开关分流**：开→新接口+新域名，关→老接口，异常→默认走老接口 |

完整需求见同目录《TMS结算业务梳理和迁移方案.md》。

## 三、核心结论

### 3.1 项目影响范围

| 项目 | 是否涉及 | 说明 |
|------|---------|------|
| `fe-match-end/match-owner-pc/app-base` | ✅ **主要涉及** | 全部 5 大模块 ~50 个接口，**改造工作量集中在此** |

> 其余前端项目（platformweb / logisticsweb / bdbl-admin / wlyd-app-consigner）经搜索确认不涉及本次迁移接口。

### 3.2 改造范围

- **改造项目**：仅 `fe-match-end/match-owner-pc/app-base`
- **改造文件**：2 个新增 + 6 个修改 = 8 个文件
- **页面层影响**：20 个页面/组件调用待迁移接口，但**无需改动**（改造在 API 层完成，调用签名不变）
- **核心难点**：前缀引用方式 4 种不统一 + 在途费用接口在 2 个文件重复定义

### 3.3 改造思路

新增统一前缀解析器，根据开关动态返回 `/lmt-user`（老）或 `/tms-settlement`（新），所有 API 文件统一引用，旧写法注释保留。在途费用重复定义用 re-export 收敛。

## 八、改造顺序建议

1. **第一步：基础设施**（其他任务依赖它）
   - 新增 `src/api/tms-settlement-switch.ts`（开关服务）
   - 新增 `src/api/tms-settlement-prefix.ts`（前缀解析器）
   - 修改 `src/config/project-config.ts`（新增 tmsSettlement 前缀）

2. **第二步：改造 reconciliation 模块**（前缀已用变量，改造最简单）
   - 修改 `src/api/reconciliation/index.ts`，`LMT_USER` 常量改为函数调用

3. **第三步：改造日常收入/支出**（硬编码需改为变量引用）
   - 修改 `src/api/financial-management/daily-income.ts`
   - 修改 `src/api/financial-management/daily-expense.ts`

4. **第四步：改造成途费用**（需先收敛重复定义）
   - 修改 `src/api/inTransit/index.ts`，GATEWAY 改为函数调用
   - 修改 `src/api/waybill/index.ts`，重复函数改为 re-export
   - 将 `findSameCostApply` 迁入 `inTransit/index.ts`

5. **第五步：接入开关+灰度验证**
   - 确认开关接口路径
   - 按模块逐步开启开关，验证新链路
