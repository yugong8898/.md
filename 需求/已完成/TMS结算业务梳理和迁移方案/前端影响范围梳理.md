## 一、迁移概述

| 维度 | 迁移前 | 迁移后 |
|------|--------|--------|
| 接口前缀 | `/lmt-user/*`（撮合结算链路） | `/tms-settlement/*`（TMS 独立结算链路） |
| 后端服务 | `lmt-orch-user` / `lmt-core-settlement` / `lgi-base-settlement` / `BMS` | `tms-orch-settlement` / `tms-core-settlement` / `tms-base-settlement`（BMS 暂不拆） |
| 数据库 | 共用 BMS 数据库 | 暂不拆分，仍共用 |
| 前端策略 | — | **接口级开关分流**：开关开→新接口+新域名，关→老接口，开关异常→默认走老接口，新服务异常→关闭开关切回老链路 |

迁移期间新老接口并行保留，前端根据迁移开关结果选择调用新接口或老接口，避免一次性全量切换。

## 四、app-base 接口调用清单（改造重点）

`fe-match-end/match-owner-pc/app-base` 中待迁移接口分布在 **5 个 API 文件**中，前缀引用方式**不统一**（这是改造难点）：

| API 文件 | 涉及模块 | 前缀引用方式 | 接口数 |
|----------|---------|-------------|--------|
| `src/api/reconciliation/index.ts` | 客户汇总、创建对账单、客户对账单、对账明细、对账单详情/更新 | `const LMT_USER = apiPrefixConfig.lmtUser` → 模板字符串拼接 | ~20 |
| `src/api/financial-management/daily-income.ts` | 日常收入 | **硬编码** `/lmt-user/income/*` | 8 |
| `src/api/financial-management/daily-expense.ts` | 日常支出 | **硬编码** `/lmt-user/expenditure/*` | 8 |
| `src/api/inTransit/index.ts` | 在途费用查询/操作/支付 | `GATEWAY = { urlGateway: '/gateway/lmt-user' }` 传参，路径**不含** `/lmt-user` 前缀 | 12 |
| `src/api/waybill/index.ts` | 在途费用（**重复定义**） | **硬编码** `/lmt-user/route-cost/*` | 4 |

> `LMT_USER` 定义位于 `src/api/reconciliation/index.ts:31`：`const LMT_USER = apiPrefixConfig.lmtUser`，来自 `@/config/project-config` 中的 `apiPrefixConfig`。

### ⚠️ 在途费用接口重复定义问题

`cost-audit`、`cost-apply-list`、`cost-delete`、`find-same-cost-apply` 在 `inTransit/index.ts` 和 `waybill/index.ts` 中均有定义，迁移时需统一处理，避免遗漏。具体重复接口：

| 接口路径 | inTransit/index.ts | waybill/index.ts |
|---------|--------------------|--------------------|
| `route-cost/cost-audit` | ✅（第 45 行，路径 `/route-cost/cost-audit`，GATEWAY 传参） | ✅（第 714 行，硬编码 `/lmt-user/route-cost/cost-audit`） |
| `route-cost-query/cost-apply-list` | ✅（第 25 行，路径 `/route-cost-query/cost-apply-list`，GATEWAY 传参） | ✅（第 722 行，硬编码 `/lmt-user/route-cost-query/cost-apply-list`） |
| `route-cost/cost-delete` | ✅（第 40 行） | ✅（第 864 行，硬编码 `/lmt-user/route-cost/cost-delete`） |
| `route-cost-query/find-same-cost-apply` | ❌ | ✅（第 872 行，硬编码 `/lmt-user/route-cost-query/find-same-cost-apply`） |

## 六、前端改造要点

### 6.1 开关分流方案（需求 6.3 节）

```
开关关闭 → 走 /lmt-user/* 老接口（现有逻辑不变）
开关开启 → 走 /tms-settlement/* 新接口 + 新域名
开关接口异常 → 默认走老接口
新服务异常 → 关闭开关，切回老链路
```

### 6.2 改造难点：前缀引用方式不统一

app-base 中 5 个 API 文件存在 4 种不同的前缀写法，需要统一为可开关切换的封装：

| 文件 | 当前写法 | 问题 |
|------|---------|------|
| `reconciliation/index.ts` | `${LMT_USER}/xxx`（变量拼接） | 变量引用，相对易改 |
| `daily-income.ts` | `/lmt-user/income/xxx`（硬编码） | 需改为变量引用 |
| `daily-expense.ts` | `/lmt-user/expenditure/xxx`（硬编码） | 需改为变量引用 |
| `inTransit/index.ts` | `{ urlGateway: '/gateway/lmt-user' }` + 路径不含前缀 | GATEWAY 对象需改，且路径拼装方式不同 |
| `waybill/index.ts` | `/lmt-user/route-cost/xxx`（硬编码） | 需改为变量引用 |

**建议方案**：新增统一的结算接口前缀解析器，根据开关返回 `/lmt-user` 或 `/tms-settlement`，所有 API 文件统一引用，避免各文件单独判断。

### 6.3 在途费用重复定义需收敛

`inTransit/index.ts` 和 `waybill/index.ts` 中重复的 `cost-audit`、`cost-apply-list`、`cost-delete` 需统一到一处，避免迁移时遗漏或重复改造。

## 九、建议改造顺序

1. **先确认待确认事项**（第 1-8 项），特别是开关方案和路径映射规则
2. **统一前缀封装**：在 `app-base` 中新增结算接口前缀解析器，根据开关返回老/新前缀
3. **按模块逐个迁移**（建议顺序）：
   - 客户汇总 + 客户对账单 + 对账明细（`reconciliation/index.ts`，前缀已统一用变量，改造最简单）
   - 日常收入 + 日常支出（`daily-income.ts` / `daily-expense.ts`，硬编码需改为变量引用）
   - 在途费用（`inTransit/index.ts` + `waybill/index.ts`，需先收敛重复定义，再统一改造）
4. **接入开关**：前端读取开关配置，动态选择前缀
5. **灰度验证**：按模块逐步开启开关，验证新链路

## 十、总结

本次 TMS 结算服务迁移，**前端改造集中在一个项目**：`fe-match-end/match-owner-pc/app-base`，涉及 5 大模块约 50 个接口调用，分布在 5 个 API 文件中。

核心改造难点是 **前缀引用方式不统一**（4 种写法）和 **在途费用接口重复定义**（2 个文件）。建议先统一前缀封装机制，再按模块逐个迁移，配合接口级开关灰度切换。

需求文档明确的服务拆分方案为新增 `tms-orch-settlement`、`tms-core-settlement`、`tms-base-settlement` 三层服务，接口前缀从 `/lmt-user` 迁移到 `/tms-settlement`，数据库暂不拆分仍共用 BMS 数据库。费用项管理作为撮合、网货、TMS 共用基础数据能力，短期继续保留在现有 BMS 服务中。
