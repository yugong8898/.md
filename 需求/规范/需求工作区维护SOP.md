## 目标

将 `.md/需求` 作为 `wlyd-workflow` 的需求工作区。原始输入、工作流阶段产物和归档资料分层保存，使每个需求可从 `workflow-state.md` 断点续传。

## 目录职责

| 目录 | 职责 |
| --- | --- |
| `待接入/` | 未识别需求编号的原始输入，等待确认编号。 |
| `进行中/<需求编号>/` | 当前需求唯一工作区；一级子目录只能使用需求编号。 |
| `已完成/<需求编号>/` | 已交付的完整工作区，保留原始资料、状态和阶段产物。 |
| `公共资料/` | 跨需求的 PRD、接口梳理和本 SOP。 |
| `归档/` | ZIP、副本与历史版本；不作为正在执行的 workflow 工作区。 |

## 新需求接入

1. 收到原始需求文档后，先识别需求编号、需求名称、所属项目和附件。
2. 已识别编号时，创建 `进行中/<需求编号>/原始需求/`，将用户投喂的原始 PRD、外部方案、测试资料及附件原样放入该目录。
3. 未识别编号时，原始资料先放入 `待接入/`；确认编号后整体移动至 `进行中/<需求编号>/原始需求/`。
4. 在工作区根目录创建 `workflow-state.md`，从阶段 0 开始执行 `wlyd-workflow`。
5. 在 `README.md` 的“进行中”记录新增需求编号。

## 工作区结构与命名

```text
进行中/
└── REQ-172/
    ├── workflow-state.md
    ├── 原始需求/
    │   ├── 原始PRD.md
    │   └── 图片和附件/
    ├── 阶段0-需求文档-REQ-172.md
    ├── 阶段1-代码分析-REQ-172.md
    ├── 阶段2-技术方案-REQ-172.md
    ├── 阶段3-实施记录-REQ-172.md
    ├── 阶段4-审查报告-REQ-172.md
    ├── 阶段5-测试用例-REQ-172.md
    ├── 阶段6-缺陷跟踪-REQ-172.md
    └── 阶段6-交付报告-REQ-172.md
```

- `workflow-state.md` 是唯一的断点续传入口，固定文件名不变。
- 正式产物统一使用 `阶段<序号>-<产物类型>-<需求编号>.md`。
- 原始资料保留原文件名，不改名、不覆盖；图片和附件与所属原始文件一起保留在 `原始需求/`。
- 未产生的阶段文件不预创建空文件。

## 阶段推进与归档

1. 每阶段完成后，更新 `workflow-state.md` 的状态、产物文件、验证证据和待确认项。
2. 需要恢复时，根据 `workflow-state.md` 的当前阶段和已存在产物继续，不重复创建已完成产物。
3. 阶段 6 通过交付门禁后，整体移动 `进行中/<需求编号>/` 至 `已完成/<需求编号>/`，不拆散工作区。
4. 副本、废弃版本和 ZIP 仅移入 `归档/`；确认无保留价值前不删除业务资料。

- [ ] `进行中/`、`已完成/` 的一级子目录均为需求编号。
- [ ] 进行中工作区包含 `workflow-state.md` 与 `原始需求/`。
- [ ] 阶段产物符合统一命名，且实际文件与状态文件记录一致。
- [ ] Markdown 相对链接在文件移动后仍可访问。
- [ ] `README.md` 的进行中、已完成和公共资料索引与实际目录一致。
- [ ] `.DS_Store`、副本和 ZIP 未混入进行中工作区根目录。
