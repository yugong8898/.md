# 二级频道页 SLUG 配置下拉化方案

面向产品与业务的方案说明。结论：**SLUG 必须由自由输入改为下拉选择**。这不是体验优化，而是本次需求 SEO 目标成立的强制前提——SLUG 保持自由输入，TDK 预置就无法覆盖新页面，本次需求的 SEO 目标直接不成立。需要产品与业务确认的是选项维护流程与锁定规则，而非是否下拉。

## 一、背景：SLUG 是什么

SLUG 是频道页的访问路径标识。本次工商财税频道启用新域名后，页面访问地址形如：

```
https://cs.wdsheng.com/{slug}
```

例如 `https://cs.wdsheng.com/gongshang-caishui`。

SLUG 同时承担三个角色：

1. **对外网址**：用户访问、搜索引擎收录、分享链接、投放物料与二维码里的地址；
2. **数据接口路径**：前台页面按 SLUG 向服务端请求页面数据，SLUG 即接口地址的一部分；
3. **SEO 配置索引**：本次需求要求每个页面的标题、描述、关键词（TDK）在上线前预置进打包配置，预置以页面地址为索引。

**SLUG 不是内部编号，是对外网址本身。** 配置时填写的每个字符，都会直接成为公开 URL。

## 二、为什么必须下拉

### 2.1 一条不可绕开的逻辑链

本次需求把频道页 SEO 列为核心目标，落地方式是 TDK 静态预置：打包前把每个页面的标题、描述、关键词写进配置，搜索引擎抓取时首屏即有正确 TDK。这条链路有一个硬前提：

```
SEO 目标成立
  → 每个页面上线时 TDK 已就位
    → 打包前必须知道所有页面的访问地址
      → SLUG 集合必须有限、已知、可枚举
        → SLUG 只能从受控清单中选择（下拉）
```

### 2.2 自由输入的风险

运营临发布时填写路径，可能与预置 TDK 使用的地址不一致。地址改动也会影响已经投放的链接、二维码及搜索收录。

## 三、方案：下拉选择 + 统一维护 + 发布后锁定

### 3.1 后台配置

- SLUG 由输入框改为**下拉选择**，选项展示为「页面名称（slug）」，所见即所得；
- 已被其他页面占用的选项置灰禁选，从源头杜绝重复；
- 选中后实时预览完整访问地址 `https://cs.wdsheng.com/{slug}`，填写人当场确认最终网址；
- 保留现有字符格式规则作为底层约束。

### 3.2 选项维护流程

- 选项清单由服务端统一维护（SLUG 注册表），后台下拉实时读取；
- 新增页面需要新 SLUG 时，走登记流程：产品/运营提报名称与用途 → 注册表新增一条 → 后台即可选择。**新增选项是配置动作，不需要版本发布**；
- 每个新页面本来就要登记 TDK 文案，SLUG 登记与 TDK 登记合并为同一流程的一步，不额外增加工作量。

### 3.3 发布后锁定

- 页面发布后 SLUG 锁定，不可直接修改；
- 确需变更时走审核流程，并同步评估旧链接跳转与收录影响，把变更成本显性化。

### 3.4 方案收益对照

| 事项 | 自由输入 | 下拉选择 |
|---|---|---|
| TDK 预置 | 地址不可枚举，新页面必然漏配 | 按 SLUG 逐条预置，上线即生效 |
| 需求验收 | SEO 验收项无法通过 | 验收项天然通过 |
| 重复/保留字 | 无拦截，生产事故风险 | 系统级杜绝 |
| 网址规范 | 命名混杂，不可控 | 统一登记，命名一致 |
| 运维配置 | 每个新地址人工同步路由与 SEO 配置 | 配置集合有限，一次预置 |
| 变更管理 | 随手改，旧链接静默失效 | 发布后锁定，变更走审核 |

## 四、为什么「保留输入 + 加校验」不成立

有一种折中思路：保留输入框，补上唯一性校验、保留字拦截、发布后锁定。这三项约束应当做，但它们**只解决事故问题，不解决枚举问题**：

1. 唯一性校验挡住重复，挡不住"打包后出现新地址"；
2. 保留字拦截挡住撞车，挡不住 TDK 覆盖不到；
3. 发布后锁定保护已发布地址，但新页面创建时地址仍是随机的。

校验加满之后，SEO 链路依然断在"地址不可枚举"这一环，本次需求的核心目标仍然不成立，漏配 TDK 的补救成本（逐页改配置、逐次发版）一分不少。**折中方案满足了安全底线，却交付不了需求目标，因此不成立。** 校验与锁定应作为下拉方案的底层约束一并保留，而不是作为自由输入的替代品。

## 五、常见疑问

**问：独立页命名需要灵活，下拉会不会不够用？**
灵活性放在选项维护流程里，不放在发布时的输入框里。新命名随时可以申请登记，登记后即可选择，命名自由度没有丢失。而"有登记"正是 SEO 预置的前提——没有登记的命名，本质上就是放弃该页面的 SEO。

**问：选项会不会不够，加选项会不会麻烦？**
选项由服务端接口下发，加选项是配置动作，不需要发版。每个新页面上线前本来就要提供 TDK 文案，SLUG 登记是同一步骤里的顺手动作，流程总步数不增加。

**问：以前一直自由填写，没有出过问题？**
此前页面数量少、无 SEO 预置诉求，问题被规模掩盖。本次需求明确要做 TDK 预置并扩展独立页面：页面数量增长后，漏配是必然事件，撞车概率同步放大。原有方式不是"没出问题"，是"还没到出问题的规模"。

**问：能不能先自由输入上线，后面再补 TDK？**
不能。补配需要改打包配置并重新发版，页面持续新增则补救永远滞后；且漏配期间页面已被搜索引擎抓取，空壳 TDK 的收录结果需要额外周期修复。先污染后治理的成本远高于一次做对。

## 六、需要产品与业务确认的事项

下拉方向是本次需求 SEO 目标的技术前提，不在可选范围。需要产品与业务确认的是落地流程：

1. **SLUG 注册表的维护责任方**：建议产品/运营提报，服务端落库维护；
2. **新 SLUG 登记流程**：与 TDK 文案登记合并为一步，确认提报与审核节点；
3. **发布后锁定规则**：SLUG 发布后锁定，变更走审核，确认审核责任方。

以上确认后研发按方案实施；TDK 预置内容清单（各页面标题、描述、关键词）按原计划由产品提供，与 SLUG 登记合并交付。
