## 2. Store 架构与扩展方案

### 2.1 现状

`stores/provider/dashboard.ts`（119 行）：
- 仅管理 `statList`（4 个指标）+ `loading` + `userName` + `newTaskCount`
- 单一 `fetchStatistics()` 方法
- 有 `statisticsRequestVersion` 防竞态机制
- `$reset()` 清理所有 state

### 2.2 扩展方案

在现有 store 中新增三模块 state，保持同一 store 管理（避免跨 store 协调轮询）：

```typescript
// 新增类型
interface DynamicModuleState<T> {
  list: T[]
  total: number
  loading: boolean
  error: boolean
}

// 新增 state
const orderDynamic = ref<DynamicModuleState<OrderDynamicItem>>({ list: [], total: 0, loading: false, error: false })
const afterSaleDynamic = ref<DynamicModuleState<AfterSaleDynamicItem>>({ list: [], total: 0, loading: false, error: false })
const opportunityRecommend = ref<DynamicModuleState<OpportunityItem>>({ list: [], total: 0, loading: false, error: false })

// 新增方法
async function fetchOrderDynamic() { ... }
async function fetchAfterSaleDynamic() { ... }
async function fetchOpportunityRecommend() { ... }
async function fetchAllDynamic() { ... }  // 并行拉取三个模块

// 轮询管理
let pollingTimer: ReturnType<typeof setInterval> | null = null
function startPolling() { ... }   // 5 分钟间隔，仅三模块
function stopPolling() { ... }
```

### 2.3 轮询策略

- **范围**：仅三模块（orderDynamic / afterSaleDynamic / opportunityRecommend），不含 statList 和 unreadStore
- **间隔**：5 分钟（300_000ms）
- **触发时机**：onMounted 首次拉取完成后启动；onUnmounted 清除
- **手动刷新**：各模块独立刷新按钮，调用对应 fetch 方法
- **主体切换**：watch providerId 时重置三模块 state 并重新拉取（复用现有 watch 机制）
- **防竞态**：每个模块独立 requestVersion，与现有 statisticsRequestVersion 模式一致

## 3. 订单详情页锚点定位可行性

### 3.1 现状

`views/provider/order/detail.vue`（707 行）：
- **无** anchor / scrollTo / hash 相关逻辑（全文搜索零命中）
- 页面结构为纵向滚动布局，关键区域通过 CSS class 标识：
  - `.bond-card` → BondCard 组件（保证金缴纳区域，位于右侧栏 side-col）
  - `.deliverable-section-card` → SingleDeliverableSection（提交交付物区域，位于主内容区 detail-main）
- 两个区域均有 `v-if` 条件控制显隐

### 3.2 锚点方案评估

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| A. URL hash + scrollTo | 跳转带 `#bond` / `#deliverable`，detail.vue onMounted 读 hash 并 scrollTo 对应 DOM | 标准做法，刷新后仍有效 | 需改 detail.vue；v-if 区域可能未渲染 |
| B. route query + scrollTo | 跳转带 `?anchor=bond`，detail.vue watch query 变化 | 不污染 URL history | 同上 |
| C. 降级跳顶部 | 不加锚点，直接跳详情页 | 零改动 | 用户体验差，不符合 R-007 |

### 3.3 建议

采用 **方案 A（URL hash）**，理由：
1. 标准浏览器行为，刷新后仍可定位
2. 改动最小：detail.vue 加一个 onMounted + nextTick scrollTo
3. v-if 问题可通过 `watch(detail, ...)` 在数据加载完成后执行 scrollTo 解决

**具体实现要点**：
- 跳转：`router.push({ path: '/provider/order/detail/:id', hash: '#bond' })`
- detail.vue：`onMounted` 或 `watch(detail)` 中，`nextTick(() => document.querySelector(hash)?.scrollIntoView({ behavior: 'smooth' }))`
- 需处理 hash 对应区域因 v-if 未渲染的情况：延迟重试或 fallback 到顶部

### 3.4 Q10 结论

锚点能力**不存在但可实现**，建议采用方案 A。待产品确认是否接受此方案（Q10）。若不接受则降级为方案 C。

## 4. 订单列表 Tab 跳转承载能力

### 4.1 现状

`views/provider/order/list.vue`：
- Tab 由接口 `getProviderOrderTabs` 驱动，前端不硬编码 tab id
- `readTabFromRouteQuery()` 读取 `route.query.tab`，默认 `'all'`
- `fetchTabs()` 返回后校验 activeTab 是否在 validIds 中，不在则回退到第一个 tab

### 4.2 跳转承载评估

- ✅ **已支持** `?tab=xx` 参数跳转
- ⚠️ **前提**：目标 tab id 必须在 `getProviderOrderTabs` 返回集中
- 若后端尚未返回「待提交交付物」tab，跳转后会 fallback 到第一个 tab（通常是「全部」）

### 4.3 Q4 影响

- 「待缴纳保证金」tab：大概率已存在（保证金是既有功能），需确认 tab id
- 「待提交交付物」tab：依赖天保新功能，可能尚未返回 → 兜底跳 `?tab=all`

| 售后 `orderNo` | `orderId`（受 G1 影响） | 是 |
| 售后 `serviceName` | `goodsName` | 是 |
| 售后 `afterSaleType` | `afterSaleType` | 否 |
| 售后 `createTime` | `applyTime` | 是 |

`dashboard/types.ts` 的 `OrderDynamicItem` / `AfterSaleDynamicItem` 为前端视图模型，联调时按上表对齐；对齐后可考虑直接改用 `ProviderOrderInfo` / `AfterSaleListItem` 并在组件内做字段映射，避免维护两套类型。
