## 全流程纵深回顾：从阶段0到阶段6的完整纠错链

第一轮复盘聚焦"暴露的问题"，本轮补充一个更深层的视角：**整个需求从误判到收敛再到稳定交付的完整纠错链路**。这条链路比单个问题更有复盘价值，因为它揭示了 AI 辅助开发中"错误是如何被逐步发现和修正的"。

### 纠错链全景

```
阶段0 误判 purchase_mode 为纯新增字段
  ↓ 用户纠正："PRD 未评审，暂停编码"
阶段0→1 语义搜索发现 orderType 已承载直采/反采
  ↓ 入口穷举确认 3 个上游取值来源
阶段1→2 服务端确认复用 orderType + canChangeOrderType 控制展示
  ↓ 技术方案锁定最小改动面
阶段3 首批编码 → ESLint 假通过 → 强制校验修正
  ↓ KeepAlive 注释编译阻塞 → 交付后修复
  ↓ 按钮/保证金非必要扩展 → 用户要求回退
  ↓ 弹窗 FriendlyTipModal → 评估后切换 ConfirmActionModal
  ↓ modeSwitchTipOpen 调试值 true → 修正为 false
阶段4 CodeReview P0/P1/P2 = 0
阶段5 测试基线 14 条 P0+P1 用例
阶段6 零改动通过 QA 全量验证
```

### 纠错链中的三个结构性特征

**特征1：用户纠偏集中在阶段0~3，阶段4之后趋于稳定**

阶段0~3 经历了 5 次用户纠偏（PRD 未评审暂停、orderType 复用、checkbox 形态确认、按钮不改、保证金回退），每次纠偏都让方案更接近真实需求。阶段4之后用户只在联调阶段反馈了弹窗组件选型和调试值两个问题，且都是定向修复，不涉及方案层面的推翻。

这说明：**前期多轮纠偏的成本在后期得到了回报**。如果阶段0直接按 PRD 字段名编码，阶段6大概率会暴露更多问题。

**特征2：AI 自发现的错误 vs 用户发现的错误比例约为 3:5**

- AI 自发现：ESLint 假通过、KeepAlive 编译漏检（回归脚本补断言）、modeSwitchTipOpen 调试值
- 用户发现：purchase_mode 误判、checkbox 形态、按钮不改、保证金回退、弹窗选型

用户发现的错误集中在**业务理解和交互边界**，AI 自发现的错误集中在**工程验证和代码细节**。这个分工模式在整个需求周期中保持一致。

**特征3：每个纠错点都有对应的防回归措施**

| 纠错点 | 防回归措施 | 是否持久化 |
|--------|-----------|-----------|
| purchase_mode 误判 | 记忆"按PRD字段名grep零命中误判" | ✅ 已入库 |
| ESLint 假通过 | 记忆"ESLint忽略规则假通过陷阱" | ✅ 已入库 |
| KeepAlive 编译阻塞 | 回归脚本补 comments:true 断言 | ✅ 内嵌实施记录 |
| 弹窗选型试错 | 记忆"ConfirmActionModal 是 FriendlyTipModal 功能超集" | ✅ 已入库 |
| DOM 可见性遗漏 | 记忆"失败回调优先复用既有收敛函数" | ✅ 已入库 |
| 过度预留 TODO | 项目规则 TODO 标注规范（待决策） | ⏳ 待落地 |
| 按钮/保证金扩展 | 最小改动原则（用户行为记忆） | ✅ 已入库 |
