## 暴露的问题

### 问题1：接口字段契约反复修正（3 轮）

| 轮次 | 字段 | 原因 |
|------|------|------|
| 第1轮 | `tPlusOneSettlement?: boolean` | 按 PRD 推测占位 |
| 第2轮 | `settlementMode: 'STANDARD' \| 'T1'` | 用户口头确认字符串枚举 |
| 第3轮 | `settlementMode: 1 \| 2` | 用户再次确认为数字枚举 |

- **根因**：契约未确认前就落地了不可逆实现
- **影响**：4 个文件改 3 遍，纯浪费
- **改进**：接口字段名/类型/层级三项必须在编码前由后端书面确认，未确认前只用 TODO 占位不写实际逻辑
- **已沉淀**：记忆 `ef0cb916`（接口字段契约未确认前不落地推测类型）

### 问题2：服务商端文件定位错误（supplier vs provider）

PRD 6.4.4 标题写"供应商"，代码分析阶段按字面定位到 `supplier/order/detail.vue`。实际目标是 `provider/order/detail.vue`。

- **根因**：PRD 用词与代码目录命名不一致，代码分析时未交叉验证路由配置或页面实际归属
- **影响**：supplier 侧改动全部回退，provider 侧重新实现
- **改进**：定位目标文件时必须通过路由表 / 页面入口 / 已有代码中的角色标识三重验证，不能只看 PRD 标题

### 问题3：接口字段层级错配（最隐蔽的 bug）

后端返回 `data.order.settlementMode`，但 provider 端 types.ts 把字段声明在了 `OrderDetailResponse` 根层级。TS 编译不报错 + 可选链静默返回 undefined → T+1 分支永远不触发，且无任何异常提示。此 bug 直到用户手动提供后端截图才发现。

- **根因**：
  - 类型定义是 AI 自己写的，写了就默认是对的，没有做三点对照
  - 可选链 `?.` 掩盖了取值错误
  - 阶段4审查只核对了"代码是否按方案实现"，没核对"方案本身的类型定义是否与后端一致"
- **影响**：T+1 功能静默失效，联调前无法发现
- **改进**：新增嵌套响应字段时强制做三点对照（API返回类型 + 类型定义层级 + 页面赋值来源）；阶段4审查增加"类型定义层级 vs 后端实际返回"核对项
- **已沉淀**：记忆 `f0af1570`（接口字段位于order子对象导致前端可选链取值恒为undefined的层级错配陷阱）

### 问题4：提示组件选型返工

初版用 `a-alert` + `:deep()` 覆盖样式，用户要求不依赖组件库内部类名 → 改为纯 div + 内联 SVG + BEM 样式。

- **根因**：技术方案阶段未与用户确认组件选型偏好
- **影响**：provider/detail.vue 样式部分重写
- **改进**：涉及 UI 组件选型时，技术方案阶段应列出候选方案并请用户确认

### 问题5：飞书测试用例获取受阻

WebFetch 鉴权失败、lark-mcp 授权超时，最终靠用户手动导出 Markdown 解决。

- **根因**：内网文档获取工具链不成熟
- **影响**：阶段5启动延迟
- **改进**：内网文档优先走"用户导出/粘贴"路径，MCP 作为长期基建推进但不阻塞当期交付
- **已沉淀**：记忆 `e8f7e2a1`（需登录态企业wiki文档网页抓取必失败应转导出或粘贴）
