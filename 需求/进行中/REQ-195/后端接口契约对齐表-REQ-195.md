## 三、前端预估的接口清单

> 以下为前端预估的接口签名，后端方案出来后逐项比对 URL 路径、请求参数、响应结构。

### 3.1 认证状态查询（C-001 待确认：可能不需要独立接口）

```
POST /v1/electronic-sign/status（路径待确认）

Request:
{
  "subjectId": "string"    // 主体ID（雇主ID 或 服务商ID）
}

Response:
{
  "code": 0,
  "data": {
    // 见第四节 ElectronicSignStatus
  }
}
```

**若后端方案不一致**：
- 若状态随 `user/info` 返回 → 本接口不需要，前端从 `userStore` 读取
- 若接口路径/参数不同 → 前端替换 URL 和参数名即可

---

### 3.2 获取协议内容

```
POST /v1/electronic-sign/agreement（路径待确认）

Request: {}（无参数，或按角色区分）

Response:
{
  "code": 0,
  "data": {
    "url": "string"    // 协议外链地址（已确认 C-002）
  }
}
```

**若后端方案不一致**：
- 若协议内容按角色/主体类型不同 → 请求参数需加 `subjectType` 等区分
- 若返回富文本而非 URL → 前端需增加 `content` 字段渲染分支（已排除，C-002 已确认）

---

### 3.3 发送验证码

```
POST /v1/electronic-sign/sms/send（路径待确认）

Request: {}（当前用户手机号，后端从 session 获取）

Response:
{
  "code": 0,
  "data": null
}
```

**若后端方案不一致**：
- 若需要前端传手机号 → 请求参数加 `phone`
- 若验证码有冷却时间 → 响应中可能需要 `cooldownSeconds` 字段

### 3.4 校验验证码并完成认证

```
POST /v1/electronic-sign/sms/verify（路径待确认）

}

{
  "code": 0,
  "data": null

```

**若后端方案不一致**：
- 若需要同时传 `subjectId` → 请求参数补充
- 若认证结果异步（需等第三方回调） → 响应结构可能变为 `submitted: boolean` + 轮询

### 3.5 提交授权委托书（仅服务商经办人）

- 若需要额外字段（如经办人身份证号等） → 请求参数补充

## 四、前端预估的数据结构

> 🔲 标记表示前端推测，待后端确认或修正。

### 4.1 ElectronicSignStatus（认证状态，C-005 待确认）

```ts
interface ElectronicSignStatus {
  certified: boolean          // 🔲 是否已完成电子签章认证
  expired: boolean            // 🔲 认证是否已过期
  expireDate?: string         // 🔲 到期日期（ISO 格式）
  reviewing: boolean          // 🔲 委托书是否审核中（仅经办人有值）
  reviewRejected: boolean     // 🔲 委托书是否审核未通过（仅经办人有值）
  authPhase?: number          // 🔲 认证阶段（用于断点恢复，与 C-006 关联）
}
```

**后端需确认/修正**：
- [ ] 字段名是否与后端实际一致
- [ ] 类型是否正确（boolean vs number vs string）
- [ ] 嵌套层级（是在 `user/info` 的 `employer`/`provider[]` 下，还是独立接口的 `data` 下）
- [ ] 哪些字段是条件性返回的（如 `reviewing`/`reviewRejected` 仅经办人场景有值，个人/法人是否省略）
- [ ] `expired` 的判断逻辑：后端是否自动计算，还是需要前端根据 `expireDate` 自行判断

### 4.2 authPhase 枚举扩展（C-006 待确认）

现有值（代码事实）：

| 端 | 现有 authPhase 值 | 含义 |
|----|-------------------|------|
| 服务商 | 0 / 1 / 2 | 0=未提交 / 1=身份认证完成 / 2=人脸认证完成 |
| 雇主 | 由 `employer.auditInfo.authPhase` 承载 | 含义类似 |

前端预估扩展值：

| 新增值 | 含义 | 对应 ViewType |
|--------|------|--------------|
| 🔲 **3** | 电子签章认证完成 | `electronicSign` 已完成 |
| 🔲 **4** | 授权委托书审核通过（仅服务商经办人） | `authLetterUpload` 已完成 |

**后端需确认/修正**：
- [ ] 新增值的具体数字
- [ ] 是否复用现有枚举体系还是另起新枚举
- [ ] 雇主端与服务商端的 authPhase 是否共用同一套扩展值

## 六、比对指南

后端技术方案出来后，按以下步骤逐项比对：

### Step 1：确认数据归属（C-001）

> 后端：认证状态是放在 `user/info` 里返回，还是单独接口？

- **若放在 `user/info`**：前端走方案B，`useElectronicSignStatus.ts` 从 `userStore` 读取，不需要独立查询接口
- **若独立接口**：前端走方案A，`useElectronicSignStatus.ts` 自行调接口

### Step 2：比对字段结构（C-005）

> 后端：拿出实际返回的字段结构，与第四节 `ElectronicSignStatus` 逐字段比对

- 字段名不同 → 前端全量替换类型定义
- 字段类型不同（如 `certified` 后端用 `0/1` 而非 `boolean`） → 前端调整判断逻辑
- 嵌套层级不同 → 前端调整取值路径
- 多出字段 → 前端忽略（不消费即可）
- 缺少字段 → 前端评估是否需要补充请求

### Step 3：比对 authPhase 枚举（C-006）

> 后端：拿出 authPhase 的完整枚举定义

- 枚举值与预估一致 → 前端无需调整
- 枚举值不同 → 前端更新 switch-case 映射表

### Step 4：比对接口路径与参数

> 后端：拿出接口文档，与第三节逐项比对

- URL 路径不同 → 前端替换常量
- 请求参数不同 → 前端调整调用处传参
- 响应结构不同 → 前端调整数据提取逻辑

### Step 5：确认消息跳转（C-004）

> 后端：消息通知中电子签章相关跳转的 path 格式

- 沿用现有 `content.path` → 前端无需调整
- 新格式 → 前端适配解析逻辑
