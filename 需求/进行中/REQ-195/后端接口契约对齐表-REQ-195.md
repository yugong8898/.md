## 零、Server 已确认契约（2026-11-05 回填）

> 来源：瑞泽《爱签核身验证技术方案》+《用户认证模块技术方案（我的部分）》+ 2026-11-05 后端技术方案评审纪要。
> 本节为**可编码的最终契约**。

### 0.1 核身域 HTTP（7 个 × 雇主/服务商两套 = 14 个对称接口）

前缀：雇主 `/v1/employer/ca-verification`、服务商 `/v1/provider/ca-verification`；`employerId`/`providerId` 字符串、互斥。前端全程只持有 `caFlowId`；中台 `agreementSerialNo`/`verifyFlowId` 不下发。响应统一 `{ code, succeed, message, model, traceId }`，`succeed=false` 时 `message` 直接弹窗、`model=null`。

| # | 方法/路径 | 请求参数 | `model` 出参 | 对应 gRPC |
|---|---|---|---|---|
| 1 | `GET /status` | query：主体 ID | `entryStatus`、`canSign`、`showSuccessEntry`、`maskedPhone` | `GetAsignIdentityVerifyStatus` |
| 2 | `POST /agreement` | body：主体 ID | `caFlowId`、`agreementUrl` | `PrepareAsignIdentityVerify` |
| 3 | `POST /send-sms-code` | body：主体 ID、`caFlowId` | `maskedPhone` | `CreateAsignIdentityVerify` |
| 4 | `POST /check-sms-code` | body：主体 ID、`caFlowId`、`verifyCode` | `canSign`、`nextAction` | `CheckAsignIdentityVerifyCode` |
| 5 | `POST /resend-sms-code` | body：主体 ID、`caFlowId` | 无 | `ResendAsignIdentityVerifyCode` |
| 6 | `POST /auth-file` | body：主体 ID、`caFlowId`、`fileName`、`fileUrl` | `nextAction` | `UploadAsignOrgAuthFile` |
| 7 | `POST /success-seen` | body：主体 ID | 无 | `MarkAsignVerifySuccessEntrySeen` |

枚举：`entryStatus`：0 未指定 / 1 去认证 / 2 继续认证 / 3 审核中（不可点）/ 4 重新上传 / 5 重新认证 / 6 即将到期（≤10 天仍可签）/ 7 认证成功。`nextAction`：0 无额外动作 / 1 经办人上传授权书 / 2 已收件等待审核。
错误文案（服务端下发）：验证码错误→「验证码错误，请重新输入」；`caFlowId` 作废→「这次认证已失效，请重新开始」。

### 0.2 认证域接口（既有改动 + 新增）

| 接口 | 性质 | 契约 |
|---|---|---|
| `POST /v1/user/info` | **既有扩展** | Server《用户认证模块技术方案》§5/§8 写有 `ProfileInfo` 透传 3 字段；本期前端已明确不消费该透传，CA 状态统一从独立 `GET /status` 读取。Server 方案是否仍实施该字段扩展，需与 Server 核对；不作为前端开发前置。 |
| `/v1/{role}/protocol` | 既有改动 | 服务端强校验 `canSign`，false 拦截「请先完成电子签章认证」；法大大 120 通道不受限；放行后回写 `authPhase=4`。前端 `GET /status` 守卫仅做 UI，服务端为兜底 |
| `POST /v1/{role}/certification/ca-auth-letter` | **新增** | 雇主：`POST /v1/employer/certification/ca-auth-letter`；服务商：`POST /v1/provider/certification/ca-auth-letter`。body 仅 `{ ossCode }`、`model=null`；以登录态定位主体。老用户/过期用户经办人补传委托书**只落物料表**；前端先调它、再调 `/auth-file`，第一步失败不调第二步 |
| `POST /v1/{role}/certification/url-2-osscode` | 既有 | 上传取 `ossCode`，供 `ca-auth-letter` 使用 |

### 0.3 与前端预估的关键差异

1. 协议 URL 非「配置/既有接口」：由 `POST /agreement` 返回，且每次调用产生新 `caFlowId`，旧未完成流程作废。
2. 老用户经办人补传为**两步调用**（`ca-auth-letter` 落物料 → `/auth-file` 提交中台），3.5 节单接口预估作废。
3. 本期前端只有一条 CA 状态消费链：固定入口、Profile、认证流程恢复与合同守卫均调用 `GET /v1/{role}/ca-verification/status`。Server 认证模块方案另写 `user/info` 三字段透传，与当前前端接入决定不一致；该差异待 Server 复核，不扩展前端 DTO/store。
4. 用户已取消前端协议内容滚动与获取验证码前等待 3 秒的门槛。Server《爱签核身验证技术方案》仍将“尚未阅读协议”列为发送短信失败的一种情况；需联调确认其阅读判定如何完成，不应在前端补回滚动或 3 秒门槛。
4. 经办人**事前身份标识字段仍缺失**：HTTP 侧只有 `nextAction=1` 事后分流，服务商 `businessSteps` 的 `isOperator` 数据源待瑞泽/认证模块补充确认。
5. 新认证用户（`is_verified=false`）经办人委托书在「完善信息」阶段由认证模块收集落库，经 `auth_file_oss_code` 交给核身域提交中台——具体页面/接口为 T1 待确认。

以下内容来自「用户认证模块技术方案」「爱签核身验证技术方案」及当日评审纪要；字段以核身方案的 HTTP 契约为准。

### 3.2 电子签章独立恢复状态（C-006 待确认）

现有代码事实：

| 端 | `authPhase` 的现有消费 | 对新流程的约束 |
|----|--------------------------|----------------|
| 服务商 | `authPhase >= 3` 进入原系统审核 | Server 提议 `4=CA完成`；前端必须将旧的范围判断改为可区分 `3` 与 `4`，否则 `4` 会被旧逻辑截胡进 systemReview。 |
| 雇主 | `authPhase === 3` 进入原认证成功态 | 新电子签章状态不能写为 `authPhase` 的新增值；**新状态枚举值不得等于 `3`**，否则被旧逻辑截胡进 certified。 |

> ⚠️ **断点恢复插入位置**：状态接口是 CA 事实来源；`authPhase=4` 仅是 Server 的 CA 完成检查点。服务商须先处理旧 `phase===3` 的审核语义，再使 `phase===4` 进入旧 `signature` 分支；雇主 `phase===3` 仍是认证成功，`phase===4` 才进入旧 `signature` 分支。

**后端需确认/提供**：
- [x] 独立状态接口、入口状态和签署准入字段已明确。
- [ ] 新认证经办人收集委托书时，`authPhase` 与状态接口的恢复组合语义。
- [ ] `authPhase=4` 的写入时机与服务商恢复分支联调验证。

前端以独立状态接口映射 `authLetterUpload`、`electronicSign` 和旧 `signature`；`authPhase=4` 仅按 Server 方案用作恢复检查点，不能替代 `canSign` 或 `entryStatus`。

## 五、实施校验指南

### Step 1：校验独立状态接口（C-001）

> 前端 Profile、固定入口、认证恢复和签署前校验均调用 `GET /v1/{role}/ca-verification/status`；该接口须返回 `entryStatus`、`canSign`、`showSuccessEntry`、`maskedPhone`。Server 认证模块方案中的 `user/info` 透传为独立待核对差异，不影响本期前端状态来源。

### Step 2：比对字段结构（C-005）

> 后端：拿出实际返回的字段结构，与第四节 `ElectronicSignStatus` 逐字段比对

- 字段名不同 → 前端全量替换类型定义
- 字段类型不同（如 `certified` 后端用 `0/1` 而非 `boolean`） → 前端调整判断逻辑
- 嵌套层级不同 → 前端调整取值路径
- 多出字段 → 前端忽略（不消费即可）
- 缺少字段 → 前端评估是否需要补充请求

### Step 3：比对电子签章恢复状态（C-006）

> 后端：拿出电子签章独立恢复字段或完整状态枚举定义

- 覆盖状态语义完整 → 前端按状态表建立恢复映射
- 缺少审核中、过期等必要语义 → 后端补充字段或前端补充查询接口
- 无论字段形式如何，前端均不使用 `authPhase` 承载电子签章状态

### Step 4：比对操作能力映射（C-007）

> 后端：拿出每项操作能力对应的实际接口或既有能力说明

- 复用已有能力 → 前端调用既有接口
- 扩展已有接口 → 前端按新增字段调整调用处
- 新增接口 → 前端增加对应封装
- 异步结果 → 明确状态刷新或轮询的触发条件

### Step 5：确认消息跳转（C-004）

> 后端：消息通知中电子签章相关跳转的 path 格式

- 沿用现有 `content.path` → 前端无需调整
- 新格式 → 前端适配解析逻辑
