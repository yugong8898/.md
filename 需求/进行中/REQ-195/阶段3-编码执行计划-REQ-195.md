# REQ-195 阶段3编码执行计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 Web PC 端完成电子合同签章认证的状态、认证流程、合同签署守卫和固定入口接入。

**Architecture:** 以独立电子签章状态作为唯一业务状态源，不改写现有实名认证 `authPhase`。接口按 Server 最终契约复用、扩展或新增；认证组件、合同守卫和固定入口都只消费统一状态层。

**Tech Stack:** Vue 3、TypeScript、Vite、Ant Design Vue、Pinia。

## 全局约束

- 仅改动 `wds/wds-web` 的 Web PC 端；不处理 APP、H5 和小程序。
- 本期合同签署守卫仅覆盖雇主“我的合同”和服务商“合同管理”。
- 未确认 C-001、C-005、C-006、C-007 与 U-009 前，不落地推测字段、接口路径或供应商入口位置。
- 不提交、不推送代码；每个编码步骤完成后执行对应验证。

> **适用范围**：仅 `wds/wds-web` 的 Web PC 端。本文只拆分执行步骤，不落地代码；实际编码以 Server 书面确认的 C-001、C-005、C-006、C-007 与产品/后端确认的 U-009 为前置条件。

**目标**：在不改变现有实名认证 `authPhase` 语义的前提下，完成电子合同签章认证在认证流程、两个核心合同入口和六处固定入口中的接入。

**实现原则**：电子签章状态使用独立状态语义；接口按业务能力复用、扩展或新增，不以候选接口数量作为实现约束；本期合同签署守卫只接入雇主“我的合同”和服务商“合同管理”。

## 步骤1：确认并固化 Server 契约

- [ ] 完成 C-001、C-005、C-006、C-007 与 U-009 的外部确认和文档回填。

**执行目标**：将 Server 的书面回复回填到契约表，形成可编码的唯一接口依据。

**输入与文件**：

- [后端接口契约对齐表](./后端接口契约对齐表-REQ-195.md)
- [阶段2技术方案](./阶段2-技术方案-REQ-195.md)

**执行内容**：

1. 对齐 C-001、C-005、C-006、C-007：状态来源、字段结构、恢复状态和操作能力映射。
2. 明确协议 URL 来源、短信发送复用结论、认证完成结果、委托书提交方式和审核结果来源。
3. 记录每个能力的实际接口、请求字段、响应示例、失败码、同步/异步行为和状态刷新方式。
4. 对齐 U-009：确认供应商个人中心的展示位置和对应主体状态来源。

**验收效果**：

- 契约表中的 C-001、C-005、C-006、C-007 均有可执行结论，不再保留候选路径作为最终实现。

- Server 明确电子签章状态不使用现有实名认证 `authPhase` 承载。

## 步骤2：建立接口适配与统一状态源

- [ ] 按最终契约建立接口适配和统一电子签章状态源。

**执行目标**：把已确认的 Server 契约封装为唯一状态来源，供认证容器、合同守卫和固定入口共同消费。

**涉及文件**：

- 新增 `wds/wds-web/src/api/electronicSign/index.ts`
- 新增 `wds/wds-web/src/api/electronicSign/types.ts`
- 新增 `wds/wds-web/src/composables/electronicSign/useElectronicSignStatus.ts`
- 条件修改 `wds/wds-web/src/stores/user.ts`：仅状态随 `user/info` 返回时修改

**执行内容**：

1. 按已确认的接口映射封装状态、协议、短信、认证完成和委托书业务能力。
2. 在 `useElectronicSignStatus.ts` 统一完成状态读取、刷新、入口状态映射和“认证成功”一次性曝光标记。
3. 保持 `authPhase` 仅服务现有实名认证流程；电子签章恢复状态从独立字段读取。
4. 为状态读取失败提供明确失败态，不把异常或空值判为已认证。

**验收效果**：

- 任一页面只通过 `useElectronicSignStatus.ts` 获取电子签章状态，不各自解析接口响应。
- 切换服务商主体后重新读取对应主体状态。
- 状态查询失败时，合同签署不放行；固定入口不展示误导性成功状态。

## 步骤3：完成电子签章与委托书组件

- [ ] 完成跨端复用的电子签章组件和服务商经办人委托书组件。

**执行目标**：完成个人/法人电子签章认证和服务商经办人委托书审核的可复用 UI 与交互。

**涉及文件**：

- 新增 `wds/wds-web/src/views/authentication/components/ElectronicSign.vue`
- 新增 `wds/wds-web/src/views/authentication/components/ProviderAuthLetterUpload.vue`

**执行内容**：

1. `ElectronicSign.vue` 实现协议 URL 展示、首次滑动后开启 3 秒验证码倒计时、验证码发送、认证完成与关闭回调。
2. `ProviderAuthLetterUpload.vue` 复用现有 OSS 上传能力，支持模板下载、PDF/JPG/PNG 校验、单文件不超过 20MB、提交审核、审核中、审核不通过及重新上传。
3. 审核意见只展示 Server 返回内容；未返回时不补造原因。

**验收效果**：

- 未滑动协议不能发送验证码；倒计时结束后才能发送。
- 个人/法人完成认证后能触发状态刷新。
- 经办人审核中不能继续签署；审核不通过可重新上传；上传失败停留当前页。

## 步骤4：接入两端认证状态机

- [ ] 将电子签章环节接入雇主和服务商认证容器，并完成独立状态恢复。

**执行目标**：在原实名认证的旧协议签署前插入电子签章环节，并保证重新进入页面时恢复到正确步骤。

**涉及文件**：

- 修改 `wds/wds-web/src/views/provider/certification/index.vue`
- 修改 `wds/wds-web/src/views/employer/certification/index.vue`

**执行内容**：

1. 服务商个人保持既有 `submitMaterials → moreInfo → faceVerify`，再在旧 `signature` 前插入 `electronicSign`；个体/企业法人保持既有 `submitMaterials → moreInfo`，再进入 `electronicSign`；经办人从 `moreInfo` 后进入 `authLetterUpload`，审核通过后进入 `electronicSign`。
2. 雇主个人和法人在旧 `signature` 前插入 `electronicSign`；不增加经办人分支。
3. 先执行既有实名认证恢复，再根据独立电子签章状态决定跳过、委托书状态、电子签章或旧协议签署。
4. 保留既有实名认证成功、审核和失败分支，不改写 `authPhase` 的既有判断。

**验收效果**：

- 服务商和雇主的原认证流程仍可按既有 `authPhase` 正确进入原结果页。
- 服务商个人完整链路为“提交材料 → 完善信息 → 人脸认证 → 电子签章认证 → 签署协议 → 系统审核”，不跳过 `moreInfo`。
- 已完成且有效的电子签章认证跳过新环节，直接进入旧协议签署。
- 经办人审核中、驳回、过期和未认证均能恢复到正确页面。

## 步骤5：接入两个核心合同签署守卫

- [ ] 将统一守卫接入雇主“我的合同”和服务商“合同管理”。

**执行目标**：确保未完成电子签章认证的主体不能从本期范围内的合同页直接进入旧合同签署。

**涉及文件**：

- 新增 `wds/wds-web/src/composables/electronicSign/useElectronicSignGuard.ts`
- 修改 `wds/wds-web/src/views/employer/contract/index.vue`
- 修改 `wds/wds-web/src/views/provider/contract/index.vue`

**执行内容**：

1. 在两个 `handleSign` 的原签署跳转或打开 URL 前调用统一守卫。
2. 已认证有效时继续原有 `handleSign` 行为；未认证或过期时按主体角色弹出电子签章或委托书补充流程。
3. 用户关闭弹窗、状态查询失败或委托书审核中时保留当前合同页，不打开旧签署 URL。
4. 认证完成后刷新状态并仅恢复本次触发的合同签署动作。

**验收效果**：

- 雇主“我的合同”和服务商“合同管理”均不能绕过认证直接签署。
- 已认证用户的原签署流程、路由和新开页行为不变。
- 本期之外的订单、下单后和分包签署入口不改动。

## 步骤6：接入六处固定入口

- [ ] 按主体状态完成六处 PC 固定入口接入；供应商入口仅在 U-009 确认后执行。

**执行目标**：在需求规定的六个 PC 页面展示与当前主体一致的电子签章入口状态。

**涉及文件**：

- 新增 `wds/wds-web/src/views/authentication/components/ElectronicSignBanner.vue`
- 修改 `wds/wds-web/src/views/employer/contract/index.vue`
- 修改 `wds/wds-web/src/views/provider/contract/index.vue`
- 修改 `wds/wds-web/src/views/authentication/personalCenter/index.vue`
- 修改 `wds/wds-web/src/views/provider/dashboard/index.vue`
- 条件修改 `wds/wds-web/src/views/supplier/personalCenter/index.vue`：仅在 U-009 确认后

**执行内容**：

1. 依据统一状态源映射未认证、认证中、审核中、审核不通过、已认证有效、已过期六种入口状态。
2. 雇主和服务商个人中心按当前身份读取对应主体状态；服务商工作台入口不替代原有实名认证横幅。
3. 已认证成功状态按主体仅曝光一次；服务商多主体之间独立记录。
4. 供应商个人中心按 U-009 的产品位置和状态来源接入。

**验收效果**：

- 六处入口与当前主体的状态一致，主体切换后不串状态。
- 已认证且有效不重复展示“认证成功”。
- 供应商入口未确认前不擅自选择展示位置或复用错误主体状态。

## 步骤7：接入消息回跳与异常处理

- [ ] 按 C-004 完成消息回跳，并统一落地异常不放行策略。

**执行目标**：保证审核结果通知、登录恢复和异常场景不丢失合同上下文，也不误放行签署。

**涉及文件**：

- 条件修改 `wds/wds-web/src/views/shared/notification/utils/inAppNavigate.ts`：仅在 C-004 规定的 `content.path` 格式需要适配时
- 修改步骤2至步骤6涉及的组件和 composable

**执行内容**：

1. 按 C-004 约定处理通知 `content.path`，保留合同、主体和回跳上下文。
2. 未登录用户完成登录后重新校验主体状态与权限，再恢复消息跳转。
3. 统一处理状态查询、验证码、上传、审核接口超时和失败：保留已填数据并提供重试入口。

**验收效果**：

- 审核通过通知可回到原合同继续签署，审核不通过进入重新上传结果态。
- 未登录通知跳转在登录后不丢失目标。
- 所有异常场景均不默认放行合同签署。
