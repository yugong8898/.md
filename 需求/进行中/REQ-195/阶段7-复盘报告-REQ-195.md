## 暴露的问题

> 分类：契约未确认 / AI 判断失误 / 实现缺陷 / 口径漂移 / 工具限制 / 流程缺失。每条附证据；已修复项注明修复提交。

### 1. 契约未确认：schema required ≠ 实际下发（P-1，两次事故同源）

- **问题**：`isAuthFileNeeded` 在 Apifox schema 标为 StatusModel 唯一 required，实际响应缺省。第一次（11-11）独立页门控 `isAuthFileNeeded !== null` 恒 false 致白屏；第二次（11-23，JL-02）新用户取码被该字段门控丢弃，验证码通过后误报「请上传授权书」并踢回提交材料。
- **根因**：把 schema 声明当运行时保证；经办人识别单源依赖 /status。
- **影响**：两次联调阻断；JL-02 首次认证主流程不可用（第二次跑因草稿落码才正常）。
- **改进**：已修——独立页兼容降级（`19fe1c2f7` 前后）+ 经办人双源识别（`20560c730`，`needsAuthFile = isAuthFileNeeded ‖ certificationIsOperator ‖ entryStatus 3/4`）。教训：契约必验项须含「required 字段实际下发抓包」，前端关键分流不得单源依赖可缺省字段。
- **证据**：workflow-state L96（白屏）、逐条验证 3.6（JL-02）、`ElectronicSign.vue:79-88`（现行双源）。

### 2. 契约未确认：预估签名与主体 id 缺口（JL-01）

- **问题**：`POST /ca-auth-letter` 联调 404，body 仅 `{ ossCode }` 缺主体 `id`；早期按对齐表预估签名开发，与实测 8 处差异。
- **根因**：后端契约未书面确认即落码（违反四件套，当时规则尚未固化）。
- **影响**：联调阻断一轮；11-10 契约切换后返工收敛。
- **改进**：已修（`8acfdcd55` 补 id）；规则 0.5「接口契约确认四件套」已沉淀（来源 REQ-171，本需求再次验证必要性）。
- **证据**：逐条验证 3.5、workflow-state L25。

### 3. AI 判断失误：横向搜索只 grep 单端接口名（RZMP-11254 雇主端误判）

- **问题**：首轮结论「雇主端无订单页直调签署链路」错误——仅 grep 服务商接口名 `postProviderSignContract`，未查雇主自有封装 `postEmployerOrderSignContract`；用户追问「雇主的呢？」后重查推翻，实测雇主 5 类签署出口均无守卫。
- **根因**：把「某一端接口名零命中」当「该业务零链路」，违反双轨制语义推演轨。
- **影响**：守卫遗漏面差点漏出交付范围；审查报告 R4-13 删除线更正。
- **改进**：已修（`51c98d959` 雇主订单 list/detail 补守卫）；教训：多端项目横向搜索必须逐端枚举自有封装函数名，grep 零命中 ≠ 不涉及。
- **证据**：workflow-state L61、审查报告 R4-13/R4-14。

### 4. AI 判断失误：UI 判定维度误判 + 文案反复（RZMP-11265）

- **问题**：按钮文案判定先按 `contractFlow`（触发来源）实现，用户纠正「需求理解错了」——维度是承载页面（`standalonePage`）；文案口径亦经「下一步→提交→确认」三变（最终 `a2f811bc2` 定为独立页「确认」，与缺陷标题预期一致）。
- **根因**：UI 展示判定维度（承载页面 / 触发来源 / 身份）未书面确认即落码。
- **影响**：两轮返工 + 文档多处口径注记；历史文档「提交」记录与最终代码漂移（本轮已修正）。
- **改进**：已修（`51c98d959` standalonePage + `a2f811bc2` 文案）；教训：UI 判定维度须与接口四件套同等书面确认。
- **证据**：`ElectronicSign.vue:138-139`（现行 `standalonePage ? '确认' : '下一步'`）、审查报告 R4-15。

### 5. 实现缺陷：前进 handler 漏排除结果态（entryStatus=3/4 分流）

- **问题**：两端容器 4 处前进 handler 只看 `isAuthFileNeeded` 未排除审核中/驳回态，3 态点下一步误入收集步、上传后协议页误显加载失败并覆盖审核中物料；首屏恢复路径已有排除故刷新正常，仅前进触发——相似场景触发来源不同未分别核验。
- **根因**：状态分流条件在「首屏恢复」与「前进」两条路径不一致，未做全状态矩阵核验。
- **影响**：用户报障一轮；3 态重传有覆盖物料副作用。
- **改进**：已修（`51c98d959` 共享集合 `CA_AUTH_LETTER_REVIEW_STATUS` + includes，4 处对称补齐，全状态矩阵核验仅 3/4 行为变化）。
- **证据**：workflow-state L64、`api/electronicSign/types.ts`。
- 〔2026-11-24 第三轮码验更正〕共享集合 `CA_AUTH_LETTER_REVIEW_STATUS` 已随 `24d1957a8`（清理遗留代码）删除，全仓 grep 零命中；现行实现为两端容器 4 处内联 `entryStatus !== CA_ENTRY_STATUS.REVIEWING && entryStatus !== CA_ENTRY_STATUS.RE_UPLOAD` 双不等链（provider L263/317、employer L328/354），排除行为与修复时等价。上文「共享集合 + includes」为 `51c98d959` 时点快照；后续同类分流改动以现行内联条件为准，勿再引用该常量。

### 6. 实现缺陷：5 秒等待触发过窄 / 送审时序差（三轮静态 check）

- **问题**：自动流转 watch 原仅「3→7」触发，首刷 2→7 卡死；认证环节 Server 自动送审时序差致首刷仍 2 时轮询不启动（当时口径）。
- **根因**：状态机边沿触发未覆盖全部前值；对服务端异步时序假设过强。
- **改进**：已修（放宽为任何非成功态→成功 + immediate；confirmAutoSubmit 确认循环——后随 11-16 送审统一口径整体废弃注释清理）。教训：状态驱动流转须枚举前值全集，服务端时序假设须联调抓包验证。
- **证据**：workflow-state L98（三轮缺陷修复）、`24d1957a8`（清理遗留代码并修复状态刷新重复流转）。

### 7. 流程缺失：文档记录超前于代码（succeed 判定）
