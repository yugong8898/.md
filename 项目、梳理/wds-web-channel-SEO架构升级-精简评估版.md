# wds-web-channel 频道落地页 SEO 架构升级方案

## 一、要解决什么

现状：纯 SPA，爬虫不执行 JS 时只有 2 个频道页能被正确收录，其余页面首屏 HTML 仅为空壳 + 骨架屏，**正文内容不可被收录**；TDK 写死在代码里，改文案要前端发版。

要做的：把落地页从「纯静态托管」升级为**区块级 SSR + CSR 混合渲染**，让爬虫拿到真实正文，同时让文案改动脱离前端发版。

## 二、架构升级内容

| 层 | 现状 | 升级后 |
|---|---|---|
| 渲染 | 全部 CSR，HTML 只有空壳 | 首屏 SEO 区块（head、顶部轮播、快捷入口、页脚）**服务端渲染进 HTML**；活动、产品、行业资讯等强时效区块**留给客户端渲染** |
| 数据 | 一个聚合接口一次返回 9 个区块数据 | **后端按区块拆接口**：SSR 只取首屏数据包并序列化进 HTML，客户端区块各取各的 |
| 服务 | 无 Node，nginx 直接吐静态文件 | 新增 **Node SSR 服务**，采用流式渲染（先吐 head 与首屏，动态区块留占位） |
| 构建 | 单次 `vite build`，一份产物 | 拆 **client + server 双产物** |
| 部署 | runner 为 `nginx:alpine`，纯静态 | 镜像 / k8s 引入 Node 运行时，nginx 增加 SSR 分流与异常回落 |
| 兜底 | — | SSR 超时或异常时回落静态壳，用户侧仍可浏览 |

## 三、难度评估

**中~高**。当前项目 SSR 基础为零，且改造同时落在渲染、数据、构建、部署四个层面：

| 难点 | 具体表现 | 为什么难 |
|---|---|---|
| ① SSR 零基础 | 仓库内 grep `server-renderer` / `renderToString` / `Nuxt` / `ssr` **0 命中**，无 Nuxt、无任何服务端渲染代码 | 服务层、渲染层、缓存层全部从零搭，团队也无 SSR 运维经验 |
| ② 数据层要重写 | 现有 `useSubChannelData.ts` 直接使用 `localStorage`、`window.location.href` 跳主站，并依赖路由守卫在浏览器侧预取整包数据 | 这三处在服务端环境会异常，是整个改造的前置卡点；同时还要把「一份数据喂 9 个区块」改成「多数据源 + 区块各自 loading / error」 |
| ③ 依赖后端同步改造 | 9 个区块当前共用一个接口的一次响应 | SSR 只渲首屏并不省后端调用，**需后端配合拆接口**，前端无法单方面完成 |
| ④ 部署链路五层同时动 | 构建脚本、Dockerfile、k8s、nginx、发布流程全部要改，且 6 套环境各自一套配置 | 任一处遗漏即造成环境行为不一致，排查成本高 |
| ⑤ 新增两类质量门槛 | hydration 一致性、CSR 区块撑高导致的 CLS | 纯静态时代不存在这两个问题，需要新的验证手段与占位设计规范 |

## 四、影响范围

**代码面（横向搜索结论）**：`sub-channel/index.vue`、`router/guard.ts`、`useSubChannelData.ts`、`channelPagePrefetch.ts`、`seoStaticTdk.ts`、`api/employer/categoryChannel/*`、9 个区块组件、`vite.config.ts`、`build/index.mjs`、`package.json`。

**配置面**：6 套 nginx conf + 6 套 Dockerfile + 2 份 k8s yaml，**共 14 个部署配置文件需同步改动**。

**协作方（均需产出，非前端内部事务）**：

| 方 | 需产出内容 | 未产出的影响 |
|---|---|---|
| 后端 | 区块级接口（拆分方案、路径、字段契约、服务端调用方式、超时 SLA、可承受并发） | 前端难以启动数据层与区块改造 |
| 运维 | 镜像内加 Node 或 k8s 加服务的许可与责任人、SSR HTML 的 CDN 缓存与刷新机制 | 环境搭不起来，代码做完也发不出去 |
| 产品 / 设计 | CSR 区块占位高度口径、运营后台 TDK 编辑入口、OG 分享图素材、sitemap 范围 | 收益兑现打折，CLS 影响体验 |

**用户可感知**：视觉内容与布局不变；首屏正文更早出现、标题不再跳变（改善）；CSR 区块若占位没做好会有页面下跳（需控制）。

## 五、开发周期与成本

> 口径：前端按 1 人投入估算；后端与运维工作量由两端各自确认。

| 投入方 | 工作量 | 说明 |
|---|---|---|
| 前端净工时 | 21~28 个工作日（4~6 周） | 含 spike 验证、数据层重构、hydration 与占位、构建部署改造、缓存降级、逐环境发布 |
| 后端接口开发 | 5~8 个工作日，可与前端并行 | **前端周期主要受此项制约**；接口晚于数据层改造完成时，整体周期相应顺延 |
| 运维配合 | 3~5 个工作日 | 镜像 / k8s / nginx / CDN 口径 |
| 整体日历周期 | 6~8 周 | 叠加方案评审、接口就绪、逐环境发布等待 |

**人力之外的成本**：

1. **新增故障域**：Node 进程带来内存泄漏、事件循环阻塞、冷启动等新一类线上问题，需纳入值班与告警范围；
2. **资源成本**：SSR 容器需占用额外 CPU / 内存配额，规格待压测后确定；若引入独立缓存组件（如 Redis），需新增设施；
3. **后端压力口径**：同一 PV 的后端请求数会上升（SSR 1 次 + 客户端 3~6 次），下降的是渲染等待与单次响应体积，**不是请求总数**，容量评估按此前提做；
4. **长期维护成本**：落地页后续任何改动都要同时考虑 SSR 与 CSR 两侧归属，比纯静态时代的改动成本高；
5. **可回收项**：nginx 摘除 SSR 分流即回落纯静态，以配置级回滚为主，退路成本较低。

## 六、主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 后端接口未配套 | 拆接口是方案成立的前提，前端无法单方面收口 | 先锁契约再进数据层改造 |
| 缓存与限流缺位直接上线 | 后端压力显著上升 | 上线前明确 TTL 与限流配套 |
| CLS 劣化 | 区块级渲染的固有副作用 | 占位高度设计 + Lighthouse 实测 |
| TTFB 变差 | 从读文件变为等接口 + 渲染 | 流式渲染 + 缓存兜底 |
| 多环境配置不一致 | 14 个配置文件需逐一同步 | 上线前逐一 diff |

## 七、待确认事项

| # | 需确认内容 | 确认方 | 未闭环的影响 |
|---|---|---|---|
| 【1】 | 后端拆几个接口、路径与字段契约、服务端怎么调（内网直连还是走网关）、超时与并发 SLA | 后端为主，运维配合 | 数据层与区块改造无法启动，优先级最高 |
| 【2】 | SSR 结果缓不缓存、TTL 多长、缓存 key 怎么定；CDN 刷新机制与生效延迟 | 后端 + 运维 + 产品 | 上线前需先具备缓存策略 |
| 【3】 | 镜像内加 Node 或 k8s 加服务，谁来改、是否允许双容器 | 运维 | 影响 spike 环境搭建与发布落地 |
| 【4】 | SSR 异常如何判定并退回静态页（超时阈值、重试、切回时机） | 前端 + 运维 | 属安全生产基线，上线前需明确 |
| 【5】 | CSR 区块占位高度口径，以及取数时机（进页即并发取 / 滚到可视区再取） | 前端 + 设计 | 占位不足会造成页面下跳，拖累 Core Web Vitals 表现 |
| 【6】 | 运营后台 TDK 编辑入口是否已具备 | 产品 / 后端 | 影响「改文案不发版」这条收益的兑现 |
| 【7】 | OG 分享图素材、sitemap 与结构化数据本次范围 | 产品 / 设计 + 评审 | 影响 SEO 效果上限，不阻塞改造 |
